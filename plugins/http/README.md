The door agents come in through: an install plugin whose host half runs in a utility process and listens on `127.0.0.1` and one port with Node's own HTTP/1.1 server. The port is the human's per-machine switch, `port.set`, which applies only on the trusted window's Confirm and reads as 4747 while none is set. The core hands it to the half in its init and starts the half again when it moves. Every request meets the checks in a fixed order before anything else reads it

- **Host.** Exactly one Host header reading `127.0.0.1` and the door's port, compared as sent, and a target that is a path. No Host, another name or port, `localhost`, a trailing dot, userinfo, another spelling of the address, two Host headers and an absolute target all answer 403. This is the DNS rebinding check
- **Origin.** Any Origin header answers 403, `null` and the door's own origin included. `Sec-Fetch-Site`, when sent, must be one header reading `none` or `same-origin`
- **Route.** `POST /mcp` over HTTP/1.1 with the exact path and no query. `GET` and `DELETE` on `/mcp` answer 405 naming `POST`, every other method or target 404, another version 505 and a request asking to upgrade 400
- **Shape of the token and the rate.** A request whose one `Authorization` is not `Bearer` and a token of RFC 6750's grammar within 2048 characters counts as one with no token: it spends a bucket of its own, 10 a second, then 429. Within it the request answers 401 without asking the seam. The agents' bucket, 50 a second, then 429, counts only a request whose token the seam took, so neither a caller with no token nor one with a token of the right shape nobody issued can spend it. Each made-up token of the right shape costs one call of the seam, which must stay cheap. Counted only for requests that passed the checks above
- **Size.** 8 KiB of headers (431) and 512 KiB of body (413), the declared length read before the body and the body counted as it arrives
- **Behind the door.** 503 while `mcp` is not ready (below)
- **Token.** A seam from the `Authorization` header's text to a client that settles later, a check that throws naming none. Two `Authorization` headers count as none. Once it settles the request is checked again and dropped unanswered when its socket closed or a request ahead of it was refused meanwhile, so no 100 Continue or body read follows. A refusal answers 401 with `WWW-Authenticate: Bearer resource_metadata="http://127.0.0.1:<port>/.well-known/oauth-protected-resource/mcp"` (RFC 9728) on the door's own port. The build that ships issues no token, so every request that gets this far answers 401
- **Node's limits.** A connection that sends nothing for 1 s is let go with the door's 408, recorded `timeout`, one that sent part of a request is left to the headers time. The strict parser, 5 s for headers, 35 s for a request, 5 s keep-alive, 100 requests a socket and 64 connections. A missing Host is left to the door's own check. A `CONNECT` meets the checks and is refused with the door's own answer, never tunnelled, an `Expect` other than `100-continue` answers 417 once the checks before the rate passed, both recorded and closed, and an upgrade is never taken. A request Node read behind a refused one on the same socket is never checked or served and a socket that closes cancels every call it carried. A socket the door answers itself past Node's response, a `CONNECT` or a parser failure, gets that answer only after every answer it owes to a request read to its end, so it is never read as the answer to an earlier request. The socket is destroyed once the answer is flushed and at the latest 35 s after the refusal, whatever the client does, a call still owed then cancelled with it

Only a request past every check is read to its end and handed on with the client the token named, every `Authorization` header taken out of what is handed on. Every response carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and a CSP of `default-src 'none'` and `frame-ancestors 'none'`, the 400, 408 and 431 the door writes for Node's parser included. Node's own 503 to a request past 100 on one socket carries none of them and no body, and a connection past 64 is dropped unanswered and recorded `full`. No `Access-Control-*` header and nothing a request sent ever reaches a response header, and an answer handed back sets only its status and body. A refusal is told by one of nine fixed reasons, `host`, `origin`, `method`, `size`, `rate`, `token`, `malformed` for bytes the parser or the door's own reading refused, `timeout` for a request too slow or a connection that sent nothing and `full` for a connection dropped at the cap, each socket's parser failure once, and the core hears them counted by reason at most once a second through `core.agentRefused`. The door writes no line anywhere and never records a Host, an Origin, a target, a token or a body. The bind takes 127.0.0.1 and the port named or fails, with no other port tried

Behind the door a request becomes one `mcp.handle` call on behalf of the client the token named. The body goes as text and is never parsed, a body that isn't UTF-8 answering 400. Only the `mcp-` headers go with it, at most 32, a name within 64 bytes and a value within 256 (431), one name sent twice answering 400. Past 8 calls in flight for a client or 32 in all the door answers 429. Each of these is recorded and closes the connection. MCP answers a status of 200, 202, 400 or 404 and a body of text or null within 4 MiB and sets no header, anything else answering 502. A call MCP or the core refused answers 503, 504, 429, 413 or 502 with a fixed body that never names the code, keeps the connection and is no refusal at the door

The door binds once on start and holds its port until `http` stops, whatever `mcp` does, so no other program takes the port while `mcp` is away. While `mcp` is not ready, starting included, `/mcp` answers 503 with the fixed body `{"error":"unavailable"}` and closes, after the checks above, the bucket for a request with no token and the declared size and before the token is looked at, whatever token came, recorded as no refusal. A well-formed token spends no bucket on a 503. The state is read at each request, so a request meets no wait while `mcp` starts. A bind that fails tells the core `port-taken` or `bind-failed` through `core.bindFailed`, which ends the half, and no other port is tried. An init that names no port binds nothing and tells `bind-failed`

`src/checks.ts` holds the checks as plain functions over the raw request and the limits as named constants. `src/server.ts` is the server, `src/mcp.ts` the serving part behind it, `src/report.ts` the refusals counted for the core, `src/keeper.ts` the plugin that opens and closes the door and `src/host.ts` the host entry with a token seam that refuses every token
