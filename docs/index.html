This is the design, not all of it runs today. The Electron app runs the core (boot, plugins-manager, router, runtime) with eleven core modules bundled into main: the gate, the grant risk classifier, flood control, the heartbeat, recording, the security view, storage, the luoshu, history, exec and the lock. The door, core code built into door.js beside main.js, runs its HTTP door and a local pipe for the hetu.exe --mcp-stdio shim in a utility process of its own, both closed while no plugin holds door.handle. The layout and hidden marks run as sandboxed first-party plugins, beside the drawer and the trusted window. OAuth, the MCP plugin, leases, net, git and artifacts are designed and not built and the map marks them planned. The older daemon runs apart from the core.

Rules the whole core keeps

The core is four parts that can't be switched off. Boot sets up trust for one run. The plugins manager checks every plugin's bytes before they run, places each plugin and gives it its identity. The router is the one path every call and event takes. The runtime keeps the isolated places plugins run in. The plugins manager calls the router and the router reaches it only through what it handed in.
Plugins have no power of their own. A sandboxed plugin runs in a Chromium worker or frame and holds one channel to the router, plus one to the drawer for its ui verbs when it holds a ui item. The router names the caller, checks the shape and the floor, asks the gate and routes. The gate decides and never routes. The real power sits in the core modules, bundled into main from the install and reviewed as core.
Mechanism in the core, policy in modules. The gate, flood control, the lock, the grant risk classifier and the security view decide and the router and the plugins manager enforce. The classifier answers for every plugin a change moves and the plugins manager orders the writes. Recording writes the log and decides nothing.
One rule for every control that judges yes or no. Switched off by the human, its step doesn't exist and answers yes. Crashed while hetu runs, it refuses. Failed at start, hetu stops in a fail-safe that offers Quit, Try again and Start with it switched off. The gate switched off lets every call pass and the log's state never enters a decision.
You can switch anything off, security included. Each widening switch needs a Confirm click in the trusted window, unless you turned Confirm off for that window's own changes, lives per machine and shows a banner while off. A security control's id is typed before it goes off.
Agents are no core identity. A chain of calls under a plugin root carries a pair: the root plugin's id plus its onBehalf field. The gate judges every call under the root call on the caller's items and the pair's. A pair may only read, list, write and lock notes and use their history, holds its items in memory for one run and a revoke lasts the run. A window's onBehalf is attribution and is never judged.
A program that targets hetu is out of scope. Plugins and MCP agents can't change the security state, since only hetu writes it, for a change a hetu window asked for and a widening one only after your Confirm click in the trusted window. A program running as you can edit the files. hetu checks each against the hash it recorded at its last write and a plugin or setting whose hash differs doesn't load. That catches careless edits but not a program that rewrites the hash too. hetu assumes the machine has no such program, which could already read and edit your notes directly.
Start narrow, widen on demand. The capability list and the editor API change only with a core API version. A version that only adds keeps older plugins loading, one that removes or reshapes what a plugin asks for refuses it.
