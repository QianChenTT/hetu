Rules the whole core keeps

The core is four parts that can't be switched off. Boot sets up trust for one run. The loader checks every plugin's bytes before they run, places each plugin and gives it its identity. The carrier is the one path every call and event takes. The runtime keeps the isolated places plugins run in. Everything that decides is a plugin in a slot the carrier asks.
Plugins have no power of their own. A sandboxed plugin runs in a Chromium worker or frame and holds one channel, to the carrier. The carrier names the caller, checks the shape and the floor, asks the gate and routes. The gate decides and never routes. Host-level plugins hold real power in Electron's main process, so they come only from the install, stay minimal and are reviewed as core.
Mechanism in the core, policy in plugins. The gate, capabilities, the watchdog and leases all follow this split: the carrier enforces, a plugin decides. The log is the core's own.
You can switch anything off, security included. Every switch needs a Confirm click in the trusted window, lives per machine and shows a banner while off. With the gate off, calls with power pass and are still logged. They need the log running, so a crashed log refuses them unless you switched the log off too. A gate or guard that is missing or crashed without you switching it off fails closed.
A program that targets hetu is out of scope. Plugins and MCP agents can't change the security state, since only hetu writes it and only after your Confirm click in the trusted window. A program running as you can edit the files. hetu checks each against the hash it recorded at its last write and a plugin or setting whose hash differs doesn't load. That catches careless edits but not a program that rewrites the hash too. hetu assumes the machine has no such program, which could already read and edit your notes directly.
Start narrow, widen on demand. The capability list and the editor API only grow with a core API version. Adding breaks nobody, removing breaks every plugin.
