The drawer: the editor window's page, core code. It holds the editor, the raw view, the quick-open palette, the views menu and the banner, takes the core keys before anything else, draws what plugins send and serves the editor bridge and the ui verbs at its end of each plugin's port. It holds no power of its own: its calls are the window's, through the window's way in, and a plugin reaches through it only what the gate gives that plugin

The page has three layers below the core layer's banner, bar, palette, raw view and menu. The base layer holds the layout's skeleton, or the drawer's plain layout while none draws, with tree views in the slots it placed. The lifted layer above it holds the editors, the titles and the frames, each laid over its placeholder and clipped to it, so no node of the layout's covers them. The overlay layer holds popovers under a strip naming their owner. Theme tokens reach the base and lifted layers only

- `preload.ts`: the window's only way to the core, `send` and `listen` on the window's IPC channel through the context bridge. Only the top frame gets it, so a frame in the window has no bridge. Main's ports to the drawer come through it too, named with the plugin and its incarnation, and reach the page by `window.postMessage`, since a port can't cross the context bridge
- `index.html`, `page.ts` and `shell.css`: the page. The core keys are taken in the capture phase: Ctrl+/ the raw view, Ctrl+P quick open, Ctrl+S save and Ctrl+Q Quit. Outside the editors a key goes to the focused view's own bindings, then the global ones. The palette, the raw view and the menu sit over everything in fixed styles, drawn as text and never markup. Drags run here on pointer events: a view's title onto the layout's zones, a node's payload onto a node that accepts it or a note's path onto an editor, a split's divider
- `link.ts`: the window's calls and events, shared by the parts below. Each event is acked once before any handler runs
- `shell.ts`: the banner from `core.status`, read again each time the core says so. Each request waiting is a notice naming the plugin it waits for, which opens the trusted window only once it has been on screen for the input delay. A button opens the plugin list
- `notes.ts`: the open notes, one instance with an opaque id per note, read through `luoshu.read` and saved through `luoshu.write` with the version read. A save names the plugins whose edits the text carries as `onBehalf`. `stale` keeps the text as a draft. A draft per note is kept in the window's storage space a second after the last change, on `core.quitting`, on a stale save and before a reload, and offered back when the note opens. A save from outside reloads a clean buffer and leaves a dirty one with a notice
- `editor.ts`: a CodeMirror view per open note, each laid over the editor slot the layout placed for it and hidden while none holds it. The current one is the note the human works in. A note saved with CRLF keeps it. Hidden marks is applied only while `core.status` names `hidden-marks` among the ready in-page plugins. A plugin's edit is its own undo step
- `hidden-marks.ts`: markdown's markers hidden and its text styled, as marks in the bridge's shape, drawn by the same code as a plugin's, so it can move behind the bridge (#98). Its switch is the `hidden-marks` install plugin. There is no loader path for in-page code
- `marks.ts`: marks drawn as CodeMirror decorations with the drawer's own classes. A plugin sends no class and no CSS
- `palette.ts`: names listed through `luoshu.list` a page at a time, up to 20 pages, and a filter that ranks a whole substring over letters in order
- `raw.ts`: which note the raw view shows: the focused instance's buffer, unsaved text included, else the note written last by anyone, with the ten written last to switch between. Whatever a plugin saved shows up here
- `keys.ts`: key names as the drawer compares them, so a binding and a key pressed meet however a plugin spelled the key
- `versions.ts`: each instance's changes counted from 0, the last 500 kept. A mark made for an older version is mapped to the text it was made for. An edit made for one is rebased through the changes since and refused `stale` only when it touches text changed since
- `surfaces.ts`: the trees the drawer keeps, one per owner and surface, each changed only by its owner's operations, at most 20 an owner
- `views.ts`: the view instances. The first of each declared view opens when its owner connects holding `ui.view`, the owner opens more, a crashed owner's first ones stay in place as down. The layout gets the manifest's title, never one set while running
- `ui-port.ts`: the ui half of each port: views drawn by their owners, the skeleton of the layout the human picked (else hetu's own, else the plain layout), `editor.open` inside the plugin's read or list scope, a frame's messages to its own worker, a view's own bindings and every event the human makes sent to the owner of the surface it happened in
- `draw.ts`: a tree drawn with the drawer's own elements, kept by node id so an input keeps its focus. Styles go in as values with `style.setProperty`, hover, focus and pressed styles apply with no round trip, text is always text, a long list draws only its rows on screen
- `layers.ts`: what each layer holds and where: views into their slots, editors, titles and frames over their placeholders, popovers next to their anchors, and what the layout plans from
- `drag.ts`: the parts of a drag with no DOM: the zone under the pointer, where in it, a payload's checks, a split's sizes held to its minimums, a press becoming a drag
- `frames.ts`: view frames, sandboxed with scripts only, from a single-use URL main mints. A port on the first load, removed with `frame.navigated` recorded on any later one. Messages are JSON text of plain data within 64 KiB, 100 a second, to and from the frame's own plugin's worker only. A frame runs in its own process, so one that loops forever leaves typing in the editor working
- `settings.ts`: the window's settings in its storage space: the layout and theme picked, favorites and the owners of keys two plugins bind
- `theme.ts`: a theme's tokens as CSS variables, the editor's colors held to 4.5 to 1 contrast or hetu's own
- `menu.ts`: the views menu, in the core layer
- `bridge.ts`: the drawer's end of each plugin's port. Main makes one for each plugin worker holding a ui item and each page load. Each message is a call shaped like CodeMirror (`editor.instances`, `read`, `decorate`, `edit`, `bind`, `keys`), served only with what `editor.reach` says the gate gives the plugin for that note: reading, decorating and editing need its `luoshu.read` there, editing its `luoshu.write` too, decorating `ui.decoration`, bindings `ui.command` and the key stream `ui.keys`. Events about a note go only to plugins that read it. What a plugin no longer reaches is taken back when the core says something changed, and what it held goes when it ends. A key two plugins bind fires for neither until the human picks its owner in the views menu. The ui verbs go to `ui-port.ts` once the plugin holds the item each needs, draws throttled past 200,000 nodes looked at a second

Measured on a 2,000-line note (#73): from the character typed on screen to a worker's mark on it, a median of 1.2 ms and 2.0 ms at the 95th percentile, over the plugin's port and back
