Runs in the Electron main process with Node. The core's four parts live here: boot, plugins-manager, router and runtime. The core only checks, places and routes. Policy, disk and process access sit with the core modules bundled into `main.js`: the gate and the grant risk classifier in `policy/`, storage, the luoshu, history and exec in `providers/`, then `flood-control/`, `heartbeat/`, `recording/` and `security-view/`, each a folder with its own door. The core plugins in `core-plugins/` hold the rest, which the plugins manager starts from verified bytes

`modules/` holds them: `wire.ts` makes them and `CoreModules` in `modules/modules.ts` starts them once as the plugins manager starts, hands them each change and answers the router's gate, providers and flood control and the plugins manager's grant risk classifier, storage's clear, heartbeat and security view while each is on. Flood control, recording and the security view run on through shutdown and the stopped mode. Recording is made by `wire.ts` over boot's log and handed to the router and the plugins manager, the holder keeping its switch. A module switched off is closed where it has a close and one switched on again is started and handed what it needs. A start or a push that throws marks the module failed until one goes through, so its calls are refused and nothing stops. The modules that judge yes or no (the gate and flood control) begin and get their first push alone first: one of them failed at start leaves every other module never begun or handed anything and puts hetu in the stopped mode. `modules/header.ts` is its door: the holder's shape, the states and records and what each module requires

`lib/` holds the logic two parts of the backend share: `data-dir.ts` (where hetu keeps its data, for boot and the runtime) and `agent-items.ts` (the schema of an agent's items, for boot's state and the plugins manager). Each part's door is its `header.ts`, holding definitions only

`wire.ts` joins the core in its order: the core modules, recording over boot's event log, the gate module's actions, the router asking the modules for the gate, the providers and flood control, then the plugins manager, which calls the router and is never called back. It hands the router the parts serving a namespace under their names in the contract's namespace table: the runtime, recording and the gate module here, the plugins manager its own as it is built, then the plugins manager's table. The Electron entry calls it once boot is done. `routerOptions` builds what the router asks for, so the plugins manager's tests run the same wiring

`main.ts` is the Electron entry that joins the parts, see `runtime/README.md`

The file helpers the folders share are in `core/lib/disk.ts`
