The runtime, one of the four parts of the core and the only one that touches Electron. `main.ts` beside this folder is the Electron entry and joins the parts

- `header.ts`: its door, what the plugins manager starts and ends plugins through (`Runtime`, `WorkerStart`, `UtilityStart`), which the plugins manager's tests fake

- `packaged.ts`: `PACKAGED` and `LOCKED`, fixed by the build into `main.js` and never read from Electron, the environment or the command line. `app.isPackaged` answers from the executable's name, so a copy of hetu named `electron.exe` would read as a run from the source
- `before-ready.ts`: what must run before Electron's `ready`, all of it synchronous. A locked build started with any argument but `--mcp-stdio` alone, or with a switch Chromium reads from elsewhere (the debugging switches, `no-sandbox`, which `ELECTRON_DISABLE_SANDBOX` sets, four that weaken the renderers and the proxy and host resolver switches that would undo the sessions' proxy or the resolver rule), exits first. Then the data folder, `userData` inside it so the single-instance lock follows the folder, the lock, the sandbox for every renderer, a host resolver rule that resolves no name in Chromium, so a frame's STUN, TURN or mDNS name is never looked up, and the `hetu` scheme registered once. The shim gets `userData` in the data folder's `shim` and no GPU and takes no lock, sandbox or scheme
- `shim.ts`: `hetu.exe --mcp-stdio`, which a program on this computer that speaks MCP over stdio starts. It runs in place of hetu with no window, lock, boot or event log and relays fd 0 to the local pipe `mcp-http-handler` serves and the pipe to stdout, since Electron's `process.stdin` reads as ended at once on Windows. With no pipe it starts hetu on its own with no arguments and waits up to 30 s for the pipe. That hetu gets nothing of the shim's environment, which is the client's choice, but the names Windows needs to start a process, with the state folder from the account's own home. An installed hetu starts the way the desktop starts it, through `explorer.exe` on Windows and `open` on its bundle on macOS, so it runs in the desktop's environment and history finds git through the desktop's PATH. On Linux it runs itself with `/usr/local/bin:/usr/bin:/bin` and a run from the source starts electron with its repo and a PATH of System32 alone. After stdin ends it keeps the pipe open whole until what it wrote went out and each request it passed on was answered, at most 35 s, since a Windows pipe breaks on a half-close and the handler cancels a closed connection's calls. It exits 0 then and 1 when stdin failed, an answer never came or the pipe or stdout went first. stdout carries only what came over the pipe and anything else goes to stderr, never to a dialog. The one exception is Electron's own: on Windows it writes `\r\n` as the very first bytes of stdout before any line of the shim's, an empty line a client reads before the first answer
- `sessions.ts`: one in-memory session per role: the editor, the trusted window and the workers. Each denies every permission, device and download, refuses every request but its own `hetu` hosts, sits behind a proxy that leads nowhere, so WebRTC has no way out over TCP either, and serves those hosts' pages from the app with a CSP. The editor page may frame and show images from the views host. The default session refuses everything
- `views.ts`: the views host, each running plugin's frames and icons served from the bytes it started with. A frame loads once from a single-use `hetu://views/<token>/` under a CSP naming only that path, with no network, frames or forms and only the editor page as its parent. Its entry page is served once and no other page, so a frame that navigates finds nothing. Icons are `svg` or `png` from `hetu://views/icon/<plugin>/`. Tokens end with their incarnation and when the editor page unloads
- `windows.ts`: the guards on every web contents (no navigation a page starts, no new window, no webview, no Bluetooth pick, no WebRTC over UDP), the web preferences every page gets, the editor window with the shell's preload and the trusted window on its own page with the same preload. In a run from the source, `HETU_QUIET_WINDOWS=hidden`, as the tests run by default, opens windows that draw and take Playwright's input and captures but sit off every display at zero opacity and can't take focus. `HETU_QUIET_WINDOWS=1` opens them without focus on another display for a person who wants to watch. A packaged build ignores both
- `electron.ts`: the plugins manager's runtime on Electron. Channels are `MessageChannelMain` ports read the way the router reads a port. Workers start and end in the hidden renderer and utility halves fork through `utility.ts`. Main's port reads only text within the plugin's cap, and a utility half's port also weighs each message against the plugin's `bytesPerSecond`, since no relay page stands in front of it
- `utility.ts`: forks a utility half (`mcp-http-handler`, as `core/api` names it) from `utility.js` beside `main.js`, with an environment built from empty, a new empty working folder in the temp folder and stdio ignored in a locked build. Its first message is the verified bytes, the plugin's limits and its port. It records each kill it makes, so an exit reads killed from that record, never from the exit code, which a kill sets to 0 on Windows
- `utility-child.ts`: the bootstrap a utility process runs. It imports the bytes main handed it as one `data:` module and runs the module's plugin on its port with the SDK's utility transport, and ends the process on anything else
- `workers.ts`: the hidden renderers that hold the workers, one per community plugin and one the first-party plugins share, each opened when its first worker starts. A community plugin's renderer closes a moment after it holds nothing. Starts wait for a page to say ready, a renderer that dies is recorded with the plugins it held, and its window skips background throttling, since its workers answer heartbeats
- `drawer-ports.ts`: a channel for each pair of a running worker whose plugin holds a ui item and an editor page load, made once the page's `dom-ready` says its preload listens, one end to the worker host page and one to the editor page, named with the plugin and its incarnation. Messages then go renderer to renderer. A worker's end is told to the page, and a new load gets new pairs
- `window-way.ts`: a window's way into the router. Its messages come only on its own webContents' IPC and the sender check refuses all but its top frame, attached, on its own `hetu` host. Each load of the window is its own caller, `{ kind: 'window', role, n }`: a new document ends the old load's way, and an answer goes only to the load that asked
- `hosts.ts`: `isPlugin`, whether a module's default export is a plugin the SDK runs, which the utility process checks. No plugin runs in main: the core modules are bundled into `main.js`. It and `utility-child.ts` are the import test's one exception: they run in the utility process (bundled apart into `utility.js`) and import the SDK
- `intrinsics.ts`: freezes the built-ins once, in `main.ts` right before the plugins manager starts, so no code in main can swap a method `core/api` decides with. `name`, `message`, `toString`, `valueOf`, `toLocaleString` and `constructor` stay settable on code's own objects
- `trusted.ts`: the one trusted window and its input delay: for a second after it shows or gains focus main drops its keyboard and mouse input, a key or button pressed meanwhile with its repeats and release included. A Confirm counts only once it armed
- `quit.ts`: Quit in its order with a deadline on each step and relaunch. `main.ts` closes the windows a human sees first and ends the hidden renderer last, so workers stop while they still run. After a failure windows hear `core.quitting` and get a two second grace. How the run ends (`Ending`) decides the restart marker: only a clean Quit clears it, while a quit after a failure, Try again and Restart hetu keep it. Try again and Restart hetu clear the start markers through the plugins manager's `triedAgain`, so a control whose start hung starts as usual at the next launch. `HETU_NO_RELAUNCH=1` in a run from the source exits without starting again, as the end-to-end tests run

`core/build/main.ts` bundles the entry into `core/dist/main.js`, the core modules among it, with the install list beside it, which names mcp-http-handler as a core plugin, the layout and hidden marks as first-party copies, all built into `core/dist/plugins`. A run from the source takes its install from there, or from `HETU_INSTALL_DIR`. A packaged build keeps the plugins beside `app.asar` and the list inside it, see `core/build/README.md`
