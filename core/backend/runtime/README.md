The runtime, one of the four parts of the core and the only one that touches Electron. `main.ts` beside this folder is the Electron entry and joins the parts

- `header.ts`: its door, what the plugins manager starts and ends plugins through (`Runtime`, `WorkerStart`, `UtilityStart`), which the plugins manager's tests fake

- `packaged.ts`: `PACKAGED` and `LOCKED`, fixed by the build into `main.js` and never read from Electron, the environment or the command line. `app.isPackaged` answers from the executable's name, so a copy of hetu named `electron.exe` would read as a run from the source
- `before-ready.ts`: what must run before Electron's `ready`, all of it synchronous. A locked build started with any argument but `--mcp-stdio` alone, or with a switch Chromium reads from elsewhere (the debugging switches, `no-sandbox`, which `ELECTRON_DISABLE_SANDBOX` sets, four that weaken the renderers and the proxy and host resolver switches that would undo the sessions' proxy or the resolver rule), exits first. Then the data folder, `userData` inside it so the single-instance lock follows the folder, the lock, the sandbox for every renderer, a host resolver rule that resolves no name in Chromium, so a frame's STUN, TURN or mDNS name is never looked up, WebRTC's mDNS hiding off (`WebRtcHideLocalIpsWithMdns` added to any `--disable-features` already there, since Chromium reads only the last), so a frame's peer connection opens no socket on 5353 and a remote `.local` candidate sends no query onto the LAN, the Blink feature `BlockingFocusWithoutUserActivation` added to any already on until Electron is on Chromium 158, which turns on the `focus-without-user-activation` policy Chromium 156 leaves experimental, so a view frame's own focus does nothing without the human's activation in it (named by the frame's `allow` and the `Permissions-Policy` its files are served with, though with the feature on a sandboxed frame is denied even with neither) and the `hetu` scheme registered once. mDNS off hides nothing only because the `disable_non_proxied_udp` policy on every web contents gathers no host candidate, so a change to that policy brings this back up. What stays is the UDP pair libwebrtc binds for each peer connection's gathering, on 0.0.0.0 and :: for the connection's life, which sends nothing and whose inbound datagrams reach nothing. No switch or policy in the app removes it. The shim gets `userData` in the data folder's `shim` and no GPU and takes no lock, sandbox or scheme. `installDirFor` names the install folder and the folder of the code built beside `main.js`, the door's among it: inside `app.asar` in a packaged build, the built main's folder in a run from the source and `HETU_INSTALL_DIR` for both in a build that isn't locked
- `shim.ts`: `hetu.exe --mcp-stdio`, which a program on this computer that speaks MCP over stdio starts. It runs in place of hetu with no window, lock, boot or event log and relays fd 0 to the local pipe the door serves and the pipe to stdout, since Electron's `process.stdin` reads as ended at once on Windows. With no pipe it starts hetu on its own with no arguments and waits up to 30 s for the pipe. That hetu gets nothing of the shim's environment, which is the client's choice, but the names Windows needs to start a process, with the state folder from the account's own home. An installed hetu starts the way the desktop starts it, through `explorer.exe` on Windows and `open` on its bundle on macOS, so it runs in the desktop's environment and history finds git through the desktop's PATH. On Linux it runs itself with `/usr/local/bin:/usr/bin:/bin` and a run from the source starts electron with its repo and a PATH of System32 alone. After stdin ends it keeps the pipe open whole until what it wrote went out and each request it passed on was answered, at most 35 s, since a Windows pipe breaks on a half-close and the handler cancels a closed connection's calls. It exits 0 then and 1 when stdin failed, an answer never came or the pipe or stdout went first. stdout carries only what came over the pipe and anything else goes to stderr, never to a dialog. The one exception is Electron's own: on Windows it writes `\r\n` as the very first bytes of stdout before any line of the shim's, an empty line a client reads before the first answer
- `sessions.ts`: one in-memory session per role: the editor, the trusted window and the workers. Each denies every permission, device and download, refuses every request but its own `hetu` hosts, sits behind a proxy that leads nowhere, so WebRTC has no way out over TCP either, and serves those hosts' pages from the app with a CSP. The editor role also owns a host for each plugin id's views, exactly `<id>.views` with each `_` written `--`, and the editor page may frame and show images from any of them (`hetu://*.views`, which Chromium matches at any depth, so `frameOwner` checks the exact host) and show the images host's notes. A frame's own policy names neither the images host nor another plugin's. The default session refuses everything
- `views.ts`: each running plugin's frames and icons on a host of the plugin's own, `hetu://<id>.views` with each `_` in the id written `--` (`viewsHost` in `api/ids.ts`), since a CSP host-source drops a host holding an underscore and the frame's own scripts would be refused. No id holds `--`, so a host names one id at most. Served from the bytes it started with. Chromium gives each host a renderer of its own, so one plugin's frames never share a process with another's. A frame loads once from a single-use `hetu://<id>.views/<token>/` under a CSP naming only that path, with no network, frames or forms and only the editor page as its parent. Its entry page is served once and no other page, so a frame that navigates finds nothing. A token or an icon asked on another plugin's host is a 404. Icons are `svg` or `png` from `hetu://<id>.views/icon/`. Tokens end with their incarnation and when the editor page unloads. Icons and the images host share one policy, `IMAGE_CSP` in `lib.ts`, under which an SVG opened as a document runs and loads nothing. At the root of each token, `hetu-theme.css` holds the theme's variables the editor page last sent with `editor.theme`, one rule on `:root`, in place of any plugin file of that name
- `images.ts`: the images host, the notes' images that plugins' image nodes name, which no plugin ever holds as bytes. The drawer asks for one URL per image it draws (`editor.image`, the editor window alone) and main mints `hetu://images/<token>` for a plugin running with a ui item whose `luoshu.read` reaches the path, at most 32 tokens waiting for one plugin and 128 in all. A token loads once within 10 s, and expired ones go at each mint and request. On its request main asks again that the plugin runs as the same incarnation and that the router's `readsNote` gives its `luoshu.read` the path, then reads the note through the luoshu's own path rules (`providers/luoshu/bytes.ts`), four notes at a time with the rest waiting so images never keep the luoshu's latches from note reads, refused past the luoshu's read cap of 16 MiB, and answers the bytes only when their first bytes sniff as the type the extension names, with that type, `nosniff`, `no-store` and `IMAGE_CSP`. Anything else answers 404. Every token ends when the editor page unloads. With the gate off by the human every read is let on, so an image anywhere in the notes is served, as hetu treats any control the human switches off
- `drag-tokens.ts`: tokens for notes dragged out of plugins' frames. The editor page asks one per note a frame draws (`editor.dragToken`, the editor window alone) and main mints 32 hex characters for a plugin running with a ui item whose `luoshu.read` reaches the note, by the router's `readsNote` asked as the plugin's worker (`reachedBy` in `images.ts`, shared with the images host). A drop on the editor hands it back (`editor.dropToken`) and main answers once with the plugin and the note, asking again that the plugin runs as the same incarnation and still reads the note. The first drop uses a token up whatever the answer. Tokens end after 30 minutes (`DRAG_TOKEN_MS` in `api/ui-limits.ts`) and when the editor page unloads, and a plugin holds 1000 at most, its oldest going first
- `lib.ts`: what the views and images hosts share with `sessions.ts`: `Served`, `ServedHost` and `IMAGE_CSP`
- `windows.ts`: the guards on every web contents (no navigation a page starts, no new window, no webview, no Bluetooth pick, no WebRTC over UDP), the web preferences every page gets, the editor window with the shell's preload and the trusted window on its own page with the same preload. In a run from the source, `HETU_QUIET_WINDOWS=hidden`, as the tests run by default, opens windows that draw and take Playwright's input and captures but sit off every display at zero opacity and can't take focus. `HETU_QUIET_WINDOWS=1` opens them without focus on another display for a person who wants to watch. A packaged build ignores both. `editorKeyOfInput` is what main does with a key of the editor window before the page or any frame hears it: a core key goes to the page whatever has focus. While focus is in a plugin's frame, by `webContents.focusedFrame`, a key that plugin's views bound goes to the page with the frame's URL, from the table the page sends with `editor.viewKeys`. `frameKeyOfInput` names the plugin's frame holding focus when Enter goes down in it with no Ctrl, Alt or Meta and no key held, which main pushes to the page on `hetu:press` as `{ key: true, url }`, never the key's text, so the page counts it as a press there for an open from that plugin's frames
- `electron.ts`: the plugins manager's runtime on Electron. Channels are `MessageChannelMain` ports read the way the router reads a port. Workers start and end in the hidden renderer and utility halves fork through `utility.ts`. Main's port reads only text within the plugin's cap, and a utility half's port also weighs each message against the plugin's `bytesPerSecond`, since no relay page stands in front of it
- `utility.ts`: forks a utility half (the door, `doorId` in `core/api`) from `utility.js` beside `main.js`, with an environment built from empty, a new empty working folder in the temp folder and stdio ignored in a locked build. Its first message is the bytes the plugins manager read once, the half's limits and its port. It records each kill it makes, so an exit reads killed from that record, never from the exit code, which a kill sets to 0 on Windows
- `utility-child.ts`: the bootstrap a utility process runs. It imports the bytes main handed it as one `data:` module and runs the module's plugin on its port with the SDK's utility transport, and ends the process on anything else
- `workers.ts`: the hidden renderers that hold the workers, one per plugin, each opened when its first worker starts and closed a moment after it holds nothing. Starts wait for a page to say ready, a renderer that dies is recorded with the plugins it held, and its window skips background throttling, since its workers answer heartbeats
- `drawer-ports.ts`: a channel for each pair of a running worker whose plugin holds a ui item and an editor page load, made once the page's `dom-ready` says its preload listens, one end to the worker host page and one to the editor page, named with the plugin and its incarnation. Messages then go renderer to renderer. A worker's end is told to the page, and a new load gets new pairs
- `window-way.ts`: a window's way into the router. Its messages come only on its own webContents' IPC and the sender check refuses all but its top frame, attached, on its own `hetu` host. Each load of the window is its own caller, `{ kind: 'window', role, n }`: a new document ends the old load's way, and an answer goes only to the load that asked
- `hosts.ts`: `isPlugin`, whether a module's default export is a plugin the SDK runs, which the utility process checks. No plugin runs in main: the core modules are bundled into `main.js`. It and `utility-child.ts` are the import test's one exception: they run in the utility process (bundled apart into `utility.js`) and import the SDK
- `intrinsics.ts`: freezes the built-ins once, in `main.ts` right before the plugins manager starts, so no code in main can swap a method `core/api` decides with. `name`, `message`, `toString`, `valueOf`, `toLocaleString` and `constructor` stay settable on code's own objects
- `trusted.ts`: the one trusted window and its input delay: for a second after it shows or gains focus main drops its keyboard and mouse input, a key or button pressed meanwhile with its repeats and release included. A Confirm counts only once it armed
- `quit.ts`: Quit in its order with a deadline on each step and relaunch. `main.ts` closes the windows a human sees first and ends the hidden renderer last, so workers stop while they still run. After a failure windows hear `core.quitting` and get a two second grace. `closeQuits` holds every close of the editor window and quits the way Quit does instead, the trusted window open or not, so the page keeps its drafts first. A close during a quit goes on, and so does one main makes itself for the stopped mode. How the run ends (`Ending`) decides the restart marker: only a clean Quit clears it, while a quit after a failure, Try again and Restart hetu keep it. Try again and Restart hetu clear the start markers through the plugins manager's `triedAgain`, so a control whose start hung starts as usual at the next launch. `HETU_NO_RELAUNCH=1` in a run from the source exits without starting again, as the end-to-end tests run

`core/build/main.ts` bundles the entry into `core/dist/main.js`, the core modules among it, with `utility.js` and the door's `door.js` beside it. hetu ships no plugin. A run from the source takes `door.js` from there, or from `HETU_INSTALL_DIR`. A packaged build keeps all three inside `app.asar`, see `core/build/README.md`
