The luoshu, a core module in main that serves `luoshu.read`, `luoshu.write`, `luoshu.remove`, `luoshu.move` and `luoshu.list` on the notes folder the human picked, and publishes `luoshu.changed` for each of its writes and `luoshu.outside` for a save made elsewhere

- **prepare** turns the path the caller wrote into the canonical one with `core/lib/canonical.ts`, which refuses a bad spelling `invalid` and a link or junction out, `.git` by any name, a dot file or dot folder at any depth and hetu's own folders `not-granted`. A dot name counts as the caller wrote it and as the disk resolved it. A path spelled with no dot that leads to a dot name, through a link or junction into `.obsidian` or the 8.3 short name of a dot name or `.git`, answers a read, a listing, a remove and the from end of a move as the same name missing would. A write or the to end of a move answers `not-granted`. So the answer doesn't tell a caller with no grant which dot names exist. The time a call takes still can: a short name or a junction that leads to a dot name answers about 60 to 140 microseconds slower than a missing name on Windows. It holds the latch on the path's key until perform or release, so no other hetu write to that name runs in between
- **a read** answers the text, the hash of its bytes and the canonical path it read, so a caller learns where the note is whatever it spelled
- **a write** checks the version it was made against under the latch: none for a new note, else the hash of the bytes read. The bytes go to a dot temp file beside the note, then a rename over it, so a crash leaves the old note or the new one. A new note lands by a hard link from the temp file in place of the rename, which fails when anything answers to the name by then: a note made since the version check under another case, a note whose 8.3 short name is the name or a folder. Such a write answers `stale` and leaves the other note as it was. A note landed by a link gets no 8.3 short name on NTFS. On a volume with no hard links the name is claimed by an exclusive create, which fails the same way, and the temp file is renamed over the claim. A crash after the link leaves the temp file as a second name of the note, and a crash before it leaves the temp file. The walk when a folder is opened removes temp files older than a minute. A read, a write, a remove and both ends of a move look at the note's folder again just before they act (`folderState`) and refuse one that no longer resolves to itself, a folder swapped for a link or a junction since prepare. A listing looks at the folder it walks the same way (`listedState`), before the walk and again after it. A folder that reads as moved is resolved once more from the caller's spelling (`looked`). When that gives the key prepare took and the path the gate judged, the call goes on with it. Another path with that key, as for a new folder another call made first in another case or a folder another program renamed in case, goes back to the gate through the call's judge and the call goes on only when the gate allows it, else it answers `not-granted`. A call the judge refuses answers the judge's own code, `not-granted` for the gate, `guard-refused` for a guard, `policy-down` for a gate that is down. A call with no judge is refused `not-granted`. The last name gets the same rule, since a look at the folder never sees a note made under another case of it: a read, the version check of a write and of a remove open the note and resolve the caller's spelling again once it is open (`named`), which has to hold the file opened at the path judged or one the gate allows through the judge, else the call answers `not-granted`. After that compare the path resolved has to resolve to itself, a file stored under that very name and not a missing name kept as the caller spelled it, and the file at it is compared once more, so a file swapped out of the name and back under another case inside the look is opened again. A note replaced at its name since the open is opened again, three times at most before `stale`. The from end of a move is looked at the same way by its file before the link or the rename and once more after the link, which is taken back when the file linked is not the one the from end holds as judged. The link is taken back only while the to end holds a file the link can have made, so a note another program made there since stays, and an unlink there that keeps failing answers `failed` with a fault for the luoshu, so a move answered refused never leaves its note at the to end too. A write's rename over a note there, a remove's move to the bin and a move's rename in place still act on the name, so right before each the name has to hold the file the version check opened, or the file a move's from end was looked at as, by file id, else the call answers `stale`. What is left for them is the time between that look and the act, for a remove the bin's own move. Writes to one key wait on each other. The key does not fold the 8.3 short name Windows gives a note another program makes, so a write spelled as that short name holds another key, and a new note's landing by a link is what keeps it off that note. A listing's folder is not judged again, since the router's canList judges each name it gives. The folders a write or the to end of a move needs are made only below the deepest one there once it resolves to itself (`madeUnder`), then one level at a time, each looked at once made, so a folder swapped for a junction while the call runs puts at most one empty folder where it leads. A write looks at the note's folder once more after the temp file is written and before the rename. What is left is the time between the last look and the act, which only opens relative to a folder handle would close
- **a remove** hands the note to the bin the runtime gives the luoshu, only at the version the remover read, the hash of the bytes, so a call with none or with an older one answers `stale` and a plugin that can write a note and can't read it can't bin it. A bin that refuses fails the remove and the note stays, and with no bin a remove answers `unavailable`
- **a move** takes the latches of both ends in key order, so two moves the opposite way round never wait on each other. It never lands on a name that exists: a hard link at the to end fails if anything is there, then the from end is unlinked. On a volume with no hard links the to end is claimed by an exclusive create and the from end renamed over the claim. A move that only changes the spelling of the note's name is one file under one latch, renamed in place. Both ends' folders are resolved again just before the disk changes, so a folder swapped for a link since prepare is refused, and the folders a to end names are made only below the deepest one that exists once that one resolves to itself, so no folder is made through such a swap
- **a listing** answers up to a page of file paths in name order under a folder, past every dot file and dot folder at any depth (`.git` and the dot temp files a write makes among them), links and hetu's own folders, with the last name as `next` when more remain. The walk leaves dot names out itself, since the router's canList passes every name with the gate off by the human. The router keeps the names the caller may list or read, and no listing carries a version
- **the watcher** is `fs.watch` with `recursive`. A path quiet for 150 ms is hetu's own write when its bytes hash as the last write hetu made there, and `luoshu.outside` otherwise. A path canonical refuses, a dot path included, publishes nothing
- with no folder picked every call answers `unavailable`

- **bytes for the image host**: `bytes.ts`'s `bytesReader` hands the provider a call of its own action, `luoshu.bytes`, which no plugin can name since the router routes only the actions `core/api` lists. It is a read in every rule above, prepare's canonical path, the latch and the looks again, and answers the note's bytes. Its judge asks the router's `reads` about the path as spelled, the canonical one and any path a look resolves it to again

`luoshu.ts` holds the logic. `core/backend/wire.ts` makes it and `core/backend/modules/modules.ts` calls its `open` with the folder at start, when the luoshu is switched on again and each time `luoshu.pick` applies. Its publish reaches the router's `publishCore` for its two topics alone and makes no audit record of a call. Switched off, its watch ends. Its tests are in `core/test/modules/luoshu`
