The carrier: the one path every call and event takes and the enforcement point on it. It binds the caller from the way in, applies the floor, asks the gate policy job and routes, a provider's call to the core module serving its namespace. It decides no grant itself. Plain Node, no Electron. Security requests and the window lifecycle actions are core actions the floor decides and never the gate, so a failed gate can't block the way out

- `carrier.ts`: the ways in (ports, host handles, the window seam with its sender check first), each message from a utility half told to the plugins manager as heard before the rate counts it, so one dropped for the rate still answers a beat, the eleven steps of a request, a Confirm refused until the trusted window armed, the log failing past `logFailMs` told to the plugins manager once, pending calls per port, `parent`, deadlines, `cancel`, `filterReadable`, the judge a call with power carries to its provider, which asks the gate and the guards again through the same step as the first judgement on the paths a look at the disk found since and moves the call's record to them, or for a call that ends refused after a refused second ask names the paths refused there, with the code the provider passes on, the core actions it serves itself, `core.agentRefused` among them, which only `mcp-http-handler`'s host half on its utility port may call and which lands as `http.refused` coalesced by reason with the counts added up, the floor for core actions, which refuses every caller for a `from` it has no rule for, the floor for `events.*` and `changed()`, which the plugins manager calls after it changes a policy job state, a plugin state or the grants snapshot. A call that ends stops its live sub-calls, so none still waits on a callee after it answers. What a callee already did stays done. Whatever the gate's state, a path with a dot segment comes back from no `filterReadable`, passes no listing's `canList`, reaches no subscriber of an event and is reached by no plugin through `editor.reach`. The gate is never asked about one
- what the plugins manager needs from it, the plugins manager's `CarrierLink`: `send` puts a lifecycle message down a half's own way and drops it for a way that is gone, `record` gives a core record's landing (landed, muted or lost), `limit` gives a limit as the carrier enforces it for one plugin and `stopping` marks the start of shutdown. From then a policy job, guard or provider that is down answers `stopped` and the bus asks the gate nothing again
- `bus.ts`: subscriptions, credits and delivery. An event is a topic and maybe a path, never content. A path reaches a subscriber only when the gate's `canRead` says so on that delivery
- `audit.ts`: `AuditWriter`, the core's own writer of the audit queue: every 100 ms up to 256 records, written as `audit.call` lines with one fsync, and `auditFields`, which maps a record to log fields. It also reads `log.segments` and `log.verify`
- the carrier answers `editor.reach` itself and filters a `luoshu.list` page and its `next` before they leave (`lister`, `listed` and `Call.canList`)
- `limits.ts`: the limits as they apply to one plugin with the human's values and the watchdog's lowering, plus the per-port rate and the flood cap
- `records.ts`: the core record lane straight through the one `EventLog` with its bounded backlog, the coalesced core records and the bounded audit queue with `next` and `ack`
- `seams.ts`: what the later parts give it, each a small interface the tests fake: the plugins manager, the gate and the providers from the core modules, the guards and the watchdog, which nothing holds yet, the prompt behind an ask and the parts that serve `ui.*` and the core actions it doesn't

The bus, in the carrier:
- `events.subscribe`, `events.unsubscribe` and `events.publish` are calls and take the eleven steps. The `event` and `ack` messages and the signals are shaped in `core/api/envelope.ts`
- a plugin publishes only the `<id>.<name>` topics its manifest declared, from any of its halves. The luoshu, a core module, publishes `luoshu.changed` and `luoshu.outside` through `publishCore`, which delivers as a publish does and makes no audit record of a call. It hears its own for free. `core.status`, `core.security` and `core.quitting` come only from the carrier and go only to windows, with no path. The trusted window hears nothing else. These floor rules hold with the gate off
- one subscription per half and topic, so a repeat replaces it, at most `topicsPerHalf` per half. A subscribe to another plugin's topics is judged at both stages under `events.subscribe` scoped by topics. One made while the gate can't be asked (failed, on with no holder or with the grants snapshot unreadable) stands until the gate allows it
- a path goes out only under the gate's `canRead`, every path with the gate off by the human whatever the log, none while the gate can't be asked. Path-less events go out while the gate is down to the subscriptions it allowed on the current grants snapshot
- a subscription the gate holds hears anything only while the gate allowed it on the current grants snapshot or the gate is off by the human. So a grants snapshot that moves while the gate is down holds back what the gate allowed on the old one. What was taken with the gate off waits when the gate is switched back on and can't be asked
- when the gate's state or the grants snapshot moves the bus asks the gate again about every subscription it holds. A refused one ends with `events.ended`. One the gate gives no answer about, a throw or an answer on an older grants snapshot included, is held back and asked about again at every sync until the gate answers. One whose item now asks at first use, as when another plugin's change moves its plugin into class 4, is in use: the ask raises the item's Confirm for the human and the subscription is held back the same way, with nothing delivered, until the Confirm lets it start or a declined Confirm or a refusal ends it. A path subscriber that the gate went down under, or a held back one that starts, gets one `events.dropped` once the gate is up, so it reads again
- at most `eventCredits` events in flight per half until its `ack`. Past them events are dropped and counted, nothing more goes out until the half has acknowledged all it was sent and then one `events.dropped` names what it missed. Signals take no credit
- a way that ends takes its subscriptions and credits with it, so a new incarnation starts with none
- records: each subscribe, unsubscribe and publish is a call with its audit record, publishes and free calls coalesced per caller per second. A subscribe whose gated topics all stand used no power, so its record names only the topics that went live and coalesces like a free call. Drops are counted in coalesced `events.dropped` core records. What stands goes in a coalesced `events.waiting` record and what asking again ended, started or held back in one `events.ended`, `events.started` or `events.waiting` record per subscriber per change, each with its topics. Deliveries and acks record nothing and recording off stops all of it

It imports nothing from `boot`
