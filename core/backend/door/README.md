The door MCP clients come in through: core code, built into `door.js` beside `main.js`, whose host half the core starts in a utility process of its own. It listens on `127.0.0.1:4747` with Node's own HTTP/1.1 server. Every request meets the checks in a fixed order before anything else reads it

- **Host.** Exactly one Host header reading `127.0.0.1:4747`, compared as sent, and a target that is a path. No Host, another name or port, `localhost`, a trailing dot, userinfo, another spelling of the address, two Host headers and an absolute target all answer 403. This is the DNS rebinding check
- **Origin.** Any Origin header answers 403, `null` and the door's own origin included. `Sec-Fetch-Site`, when sent, must be one header reading `none` or `same-origin`
- **Route.** `POST /mcp` over HTTP/1.1 with the exact path and no query. `GET` and `DELETE` on `/mcp` answer 405 naming `POST`, every other method or target 404, another version 505 and a request asking to upgrade 400
- **Rate.** 50 requests a second, counted only for requests that passed the checks above, then 429
- **Size.** 8 KiB of headers (431) and 512 KiB of body (413), the declared length read before the body and the body counted as it arrives
- **Token.** A seam from the `Authorization` header's text to a client. Two `Authorization` headers count as none. The build that ships issues no token, so it answers 401 with a bare `WWW-Authenticate: Bearer`
- **Node's limits.** The strict parser, 5 s for headers, 35 s for a request, 5 s keep-alive, 100 requests a socket and 64 connections. A missing Host is left to the door's own check. A `CONNECT` meets the checks and is refused with the door's own answer, never tunnelled, an `Expect` other than `100-continue` answers 417 once the checks before the rate passed, both recorded and closed, and an upgrade is never taken. A request Node read behind a refused one on the same socket is never checked or served and a socket that closes cancels every call it carried. A socket the door answers itself past Node's response, a `CONNECT` or a parser failure, gets that answer only after every answer it owes to a request read to its end, so it is never read as the answer to an earlier request. The socket is destroyed once the answer is flushed and at the latest 35 s after the refusal, whatever the client does, a call still owed then cancelled with it

Only a request past every check but the label's is read to its end. A token naming a label outside `<client id>#<n>` is then answered 401 as `token`, and any other is handed on with the client the token named. Every response carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and a CSP of `default-src 'none'` and `frame-ancestors 'none'`, the 400, 408 and 431 the door writes for Node's parser included. Node's own 503 to a request past 100 on one socket carries none of them and no body, and a connection past 64 is dropped unanswered. No `Access-Control-*` header and nothing a request sent ever reaches a response header, and an answer handed back sets only its status and body. A refusal is told by one of eight fixed reasons, `host`, `origin`, `method`, `size`, `rate`, `token`, `malformed` for bytes the parser or the door's own reading refused and `timeout` for a request too slow, each socket's parser failure once, and the core hears them counted by reason at most once a second through `core.refused`. The door writes no line anywhere and never records a Host, an Origin, a target, a token or a body. The bind takes 127.0.0.1 and the port named or fails, with no other port tried

Behind the door a request becomes one `door.handle` call on behalf of the label the token named, which the core delivers to the one plugin holding the role `door.handle`: the client id, `#` and the number of the authorization with no leading zero, the client id within 255 of the characters a URL holds as written and the number within 15 digits. A label out of that form answers 401 and is recorded as `token`, since the core takes any field and the form is the door's own check. The body goes as text and is never parsed, a body that isn't UTF-8 answering 400. Only the `mcp-` headers go with it, at most 32, a name within 64 bytes and a value within 256 (431), one name sent twice answering 400. Past 8 calls in flight for a client or 32 in all the door answers 429. Each of these is recorded and closes the connection. The holder answers a status of 200, 202, 400 or 404 and a body of text or null within 4 MiB and sets no header, anything else answering 502. A call the holder or the core refused answers 503, 504, 429, 413 or 502 with a fixed body that never names the code, keeps the connection and is no refusal at the door

The door and the pipe are open exactly while `door.handle` is served, which the core tells in `deps` by the role's action: bound on start and on every change the core tells, closed when the role's holder goes. The door holds no grant, since the floor admits the call to the role from the utility process the core started and the door names no plugin. A bind that fails tells the core `port-taken` or `bind-failed` through `core.bindFailed`, which ends the half, the pipe's always `bind-failed`. The door makes it as a raw core call with `ctx.call`, since the floor takes it from this half in its utility process alone and no other plugin's context carries it. No other port or name is tried

The clients that reach hetu over a transport with no token, the local pipe, join through `clients.ts`. Each connection gets a label of its own, the client id, `#` and the clock's milliseconds kept above the last number given, so no label is given twice in a run of hetu, a restart of the half included. A session of a client confirmed earlier asks `core.identities` once before it joins and is turned away when the client was revoked or the core can't answer. The human confirms a client once a run through `core.consentAsk` with no redirect, its answer collected through `core.consentAnswer` and later sessions of a confirmed client join with no connect of their own, sessions joining while its connect waits waiting for that one. A connect the core refuses `not-granted` is for a client the core holds already, one connected before this half restarted, so it joins unless `core.identities` says it was revoked. Every few seconds `core.identities` is asked about each client with an open connection and a revoked one has every connection closed and is turned away for the run

The local pipe is the way in for a program on this computer, the shim `hetu.exe --mcp-stdio` relaying an MCP client's stdin and stdout. Its name is one a user from `pipeName` in the contract: `\\.\pipe\hetu-mcp-<user>` on Windows, where the first server of a name keeps it. Elsewhere it is `/tmp/hetu-mcp-<user>/mcp.sock` in a folder made for its owner alone, one already there taken only when it is the user's own and no one else may open it. A socket left there is taken away only when no server answers on it and anything there that is no socket stays. A dev hetu and an installed one share the name as they share the port. It reads MCP's stdio framing, one message a line of at most 512 KiB, a line past it refused as `size` before its end arrives and the connection closed. The first line spends the door's rate and must name its client by a `clientInfo.name`, else `malformed` with the error -32602: an `initialize`'s own `params.clientInfo` or, for MCP from 2026-07-28 on, which has no `initialize`, the `io.modelcontextprotocol/clientInfo` in any request's `params._meta`, such as the `server/discover` a client of both eras sends first. The first line is passed on as it came, so answering it is the job of the role's holder. The client joins through `clients.ts` with `clientInfo.title` as the name the connect shows when given, a client refused counted as `token`. A first line refused is answered with a JSON-RPC error carrying its id before the connection closes. Lines sent behind it are held until the client joined, within the same 512 KiB. Every line then spends the door's rate and goes to the same serving part as the door's on behalf of the connection's label with no headers, so the caps on calls in flight hold across both. An answer's body goes back as one line and an answer with none, a notification's 202, writes nothing. A request past the rate or the calls in flight is recorded as `rate`. It and one the serving part answers with a fixed body get a JSON-RPC error with the request's id and the fixed body's word, `unavailable`, `timeout`, `throttled`, `too large` or `bad gateway`. The connection stays. Only the id is read from the line for it and a notification gets nothing. Bytes that are no UTF-8 close the connection as `malformed`. A connection that ends gets what was written before its end, at the latest 35 s later. A connection that closes cancels every call it carries and leaves the clients table, at most 64 connections at once

`checks.ts` holds the checks as plain functions over the raw request and the limits as named constants. `server.ts` is the server, `mcp.ts` the serving part behind it, `report.ts` the refusals counted for the core, `rate.ts` the rate every listener shares, `clients.ts` the clients over a transport with no token, `pipe.ts` the local pipe, `keeper.ts` the plugin that opens and closes the door and the pipe and `host.ts` the host entry on 127.0.0.1:4747 and the user's pipe with a token seam that refuses every token
