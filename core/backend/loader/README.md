The loader, one of the four parts of the core: what may run, where, when and as whom. It reads the install list and every manifest with the strict parser, reads each plugin's files once and keeps the bytes that run, applies the signer pairing and the reserved ids and places each plugin by where its code came from. It resolves the requires graph, mints every port and handle and registers it with the carrier in the same step and owns every plugin's lifecycle state. It runs no plugin code, decides no grant and restarts nothing on its own. Plain Node, no Electron

- `loader.ts`: the `Loader` the carrier's seam names, the install check, the first-party reconcile, the plugin folder scan, the start order, starts, stops, crashes and restarts, the start markers, app updates to install plugins, staged updates against the live graph, each refused unless its version is newer and applied from the bytes it hashed only after the human's Confirm, the numbered `StateView` and the one entry that applies a confirmed change through the `StateStore`. The security controls start alone first: one that is on and fails stops hetu in the stopped mode. One that fails while hetu runs asks the runtime to quit and start again once. It serves `watchdog.stop` and `watchdog.restart`, the security requests, `security.list` and the human's stop and restart on the carrier's core seam. A first-use ask it raises as a held `item.on`. It serves `core.status` and `core.views`, hands the notes folder and the data folder to the luoshu and history (`openLuoshu`, `openHistory`) and the OS's bin main gives (`shell.trashItem`) to the luoshu alone and exec its view of the grants (`execView`, `pushExec`), asks the capabilities slot for a plugin's class and first-use list at an approval, handing it what the plugin reaches through `plugin.call` and where data moves to and from it (`flow`: calls both ways, a subscription from the topic's owner to the plugin that hears it) and clears a plugin's storage through the storage plugin. After any change to what one plugin holds it classes again every other plugin whose links the change moves (`moved`), from the state the change asks for, so the Confirm names the classes it raises before it applies. Their entries are written in the change's turn, a raised one before the change and a lowered one after (`settle`). At every start, after the first-party reconcile and before the plugin folder is scanned, it classes every plugin-folder entry again from the graph as it stands (`classAll`) and writes only an entry whose class or list comes out different. An item that asks and that the entry doesn't list counts as confirmed only when the entry's class is 4 or null and the item asks with no links at all, or the install is the one the last start recorded (`installAsLast`). With the slot down nothing is classed again
- `requests.ts`: the security requests: a narrowing change applies at once, a widening or destroying one waits under a core id with the fingerprint of the state it read until the trusted window's Confirm, whose record lands before anything applies
- `graph.ts`: the requires graph as a pure function: cycles refused, a dependent waiting on its first direct requirement that can't serve it and the order every start and stop follows
- `verify.ts`: one read of a plugin folder, its hash and its manifest parsed from the bytes read, with what a read alone can refuse
- `folders.ts`: the loader's folders in the data folder: staging, the swap that puts a copy or an update in place before its entry, the start markers, the restart marker (`failed-once`) and the marker of each install plugin's version from the last run
- `seams.ts`: what it needs from the carrier beyond `register`, `handle` and `end` and from the runtime, each a small interface the tests fake. The carrier gives it all. `core/backend/wire.ts` builds the two in order

It imports `firstPartyPath` and the state's types from `boot` and nothing from the carrier but its seam types
