The plugins manager, one of the four parts of the core: what may run, where, when and as whom. It reads the install list and every manifest with the strict parser, reads each plugin's files once and keeps the bytes that run, applies the signer pairing and the reserved ids and places each plugin by where its code came from. It resolves the requires graph, mints every port and registers it with the router in the same step and owns every plugin's lifecycle state. It starts the core modules once the install list is read, hands them each change and switches them as the human does. It runs no plugin code, decides no grant and restarts nothing on its own. Plain Node, no Electron

`PluginsManager` is one class built as a chain, each file a class holding one job and extending the one below it, each member moved as it was. A step of a part above that a part below calls is declared there as abstract

- `base.ts`: what every part shares: the options, the fields, the constructor, the router's seam (`policyJob` reads a core module's state, the gate and the grant risk classifier among them, an expected guard the human switched off reading off and any other id absent), the small readers and writers every step uses (`note`, `record`, `landing`, `serial`, `bump`, `putEntry`, `writeSwitches`) and how a plugin's status is judged. A core module's id names no plugin and a security control is required by no plugin
- `lifecycle.ts`: the requires graph planned again on every change, each plugin's state, the pump that stops in reverse graph order and starts in graph order, starting and stopping incarnations, crashes, the heartbeat's marks and kills, the stops the human asked for and the stopped mode. Every change is told to the router. When that throws it records a fault (`router`, `changed`) and has the router end every open call with power a plugin holds (D-646). Each core module is a node of the graph, ok while on, so a plugin requiring the luoshu waits while it is off or failed. The log failing while hetu runs asks the runtime to quit and start again once
- `identities.ts`: the pairs' state, in memory for the run and in no state file: each pair's items by the root plugin's id and the grant key of the field, so each session of one client shares the client's items, ask and revoke, the pairs the human revoked and a count per pair that an ask waiting for it goes stale against. The ask comes from the plugin the root of a chain called, for that chain's pair. It also raises the ask behind the gate's first-use prompt
- `classes.ts`: every class change goes through one function (`classes`), a change to one plugin or a pass over every entry. It hands the grant risk classifier the whole table (every plugin the plugins manager knows with what it holds and what its entry stores, the change, its cause and whether a Confirm for it is on screen), checks the answer with the contract's shape check and stores what it answers: the class, the items that ask at first use but those the entry's `confirmed` record names and the notice owed. With the classifier switched off a pass leaves each entry as stored and a change passes: every entry keeps its class, is marked `unclassed` and lists every item not confirmed. Down, a throw or an answer the check refuses, every entry's class is not known and every item asks, since without an answer nothing tells which plugins a change moves. Which entries rise is read from the class numbers stored, never from the classifier: a rising entry is written before the change and a lowering one after it (`settle`). A notice owed is raised from the entry after the change and at every start (`raiseOwed`) until the human answers it. At every start, after the first-party reconcile and before the plugin folder is scanned, every entry is classed again (`classAll`) and again once the human switches the classifier on in the run
- `install.ts`: the install list read and checked, the first-party copies reconciled with it, the tombstones and every plugin in the plugin folder found, read once and verified before it runs. An install list that doesn't check out stops hetu in the stopped mode
- `changes.ts`: applying a change the human confirmed or one that narrows (`applyNow`), grants widened and narrowed, item switches, plugins switched, approved, removed, restored and reset, the numbered grants snapshot with exec's view of it and staged updates resolved against the live graph, each refused unless its version is newer. An update loads on its own only when the grant risk classifier answers that it does, so never while it is off or down
- `plugins-manager.ts`: `PluginsManager` joining the parts: the actions it serves on the router's core seam (`core.status`, `core.views`, `security.list` and the human's stop and restart), what a request's Confirm says, the banner and the start. The start runs the core modules once the install list passed. Its checks read the contract's `failSafeControls`: the gate, flood control and every expected guard. A start marker the run before left for one of them means its start hung main, so hetu stops in the stopped mode naming it with the reason `START_HUNG` before any module begins. A marker of a control the human switched off holds nothing back and is cleared. Starting with it switched off clears the marker, Try again clears every marker (`triedAgain`) and Quit keeps it. Shutdown and a clean Quit wait for every marker write and clear under way (`markerWork`). An expected guard no core module holds stops hetu in the stopped mode before any module begins, unless the human switched it off, which `policyJob` reads as off as the router does. Starting with it switched off writes its switch though no plugin holds it. A control that judges yes or no that failed at start stops it before any other module begins or any plugin runs, where the human quits, tries again or starts with it switched off, which counts as switching it off. No restart marker is written for it, so it never starts again on its own
- `requests.ts`: the security requests: the queue, the fingerprint of the state each read, the stale check and record-before-apply. The security view module decides whether a change applies at once, lands its record and applies or waits for the trusted window's Confirm and whether a click counts. With the view off every change a window asks for applies unasked with its record first and the editor window may only switch the view on again. A throw of the view applies nothing and answers `failed`
- the heartbeat, recording and the security view are core modules the plugins manager calls through their doors: it tells the heartbeat each plugin ready, heard and stopped and does the ping, the mark and the kill it asks for, records through recording only while it is on and hands requests to the security view. With the security view off the stopped mode shows in the native box
- `graph.ts`: the requires graph as a pure function: cycles refused, a dependent waiting on its first direct requirement that can't serve it and the order every start and stop follows
- `verify.ts`: one read of a plugin folder, its hash and its manifest parsed from the bytes read, with what a read alone can refuse
- `folders.ts`: the plugins manager's folders in the data folder: staging, the swap that puts a copy or an update in place before its entry, the restart marker (`failed-once`), the start markers (`starting/<id>`, one empty file per judging control whose start runs) and the marker of each core plugin's version from the last run
- `connects.ts`: the connect a utility half asks for, held in memory until the same plugin collects the human's answer. A connect for a client the core holds already is refused. A client on this computer reaching the plugin over its local pipe connects with no redirect
- `reads.ts`: the views and plugin rows the router reads
- `header.ts`: what it needs from recording, a small interface the tests fake. It calls the router through the router's door and hands it, as it is built, the actions it serves under its part's name, its asks and its listeners for a closed way and for what a half sent, so the router never calls it but through those. `core/backend/wire.ts` builds the two in order. What it needs from the runtime the runtime announces in its own `header.ts`

It imports the state's types from boot's `header.ts`, the runtime's from the runtime's `header.ts`, nothing from the router but `header.ts`, the router's door. It reaches the grant risk classifier through the modules holder's door with its interface typed in the contract (`core/api/classes.ts`). `firstPartyPath` is in `folders.ts`, the one part that resolves install paths

## Fetching from GitHub

Main's one way to the network, apart from the chain. Every window stays offline. Nothing calls it yet

- `github.ts`: a GET with Node's own fetch to `api.github.com`, `github.com` or `release-assets.githubusercontent.com` over https with no user or port (`onGitHub`). Each redirect is checked against the same hosts before it is followed (`redirect: 'manual'`, five at most). No cookie or credential is sent and every request names the client `hetu-installer`. The byte cap is counted as read and refused early by a Content-Length past it. One time limit covers the request with its redirects and body. A failure answers one of `fetchProblems`, each with words the trusted window can show (`fetchProblemWords`): a 404 is `not-found`, which `releaseZips` answers as `no-release` for the API, a 429 or a 403 with no requests left or a time to wait is `rate-limited` and a fetch or a body read that rejects is `offline`
- `release.ts`: a pasted `https://github.com/<owner>/<repo>` link, its releases page, its latest release or a release by tag read (`githubLink`), the release asked of the API (`releaseZips`, 8 MiB and 20 s) and its `.zip` assets uploaded whole answered with their name, size, download link and the sha256 GitHub gives, null when it gives none. A sha256 that is not 64 hex digits refuses the answer. An answer whose download link leaves GitHub's hosts is refused whole. `downloadZip` fetches a picked zip's bytes under 72 MiB, the 64 MiB the unpacking writes at most plus room for a zip's headers, in ten minutes at most, refused before any request when the release says it is bigger and refused as `digest-mismatch` when the bytes downloaded do not hash to the sha256 given. Its answer says whether the bytes were checked (`verified`). The digest comes in the same API answer as the download link, so it is integrity only: it shows the bytes arrived as GitHub holds them and says nothing of who made them
