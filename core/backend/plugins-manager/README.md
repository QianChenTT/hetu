The plugins manager, one of the four parts of the core: what may run, where, when and as whom. It reads the install list and every manifest with the strict parser, reads each plugin's files once and keeps the bytes that run, applies the signer pairing and the reserved ids and places each plugin by where its code came from. It resolves the requires graph, mints every port and registers it with the carrier in the same step and owns every plugin's lifecycle state. It starts the core modules once the install list is read, hands them each change and switches them as the human does. It runs no plugin code, decides no grant and restarts nothing on its own. Plain Node, no Electron

- `plugins-manager.ts`: the `PluginsManager` the carrier's seam names, the install check, the first-party reconcile, the plugin folder scan, the start order, starts, stops, crashes and restarts, app updates to core plugins, staged updates against the live graph, each refused unless its version is newer and applied from the bytes it hashed only after the human's Confirm, the numbered `grants snapshot` and the one entry that applies a confirmed change through the `StateStore`. An install list that doesn't check out stops hetu in the stopped mode. The log failing while hetu runs asks the runtime to quit and start again once. Each core module is a node of the requires graph, ok while on, so a plugin requiring the luoshu waits while it is off or failed. A core module's switch is in `switches.off`, its row in `security.list` comes from the core and Recover refuses it. It serves `watchdog.stop` and `watchdog.restart`, the security requests, `security.list` and the human's stop and restart on the carrier's core seam. A core plugin in `utilityIds` (`mcp-http-handler`) is placed `utility`: its host entry runs in a utility process of its own on a port main counts, with no data folder, killed when it misses its heartbeats and restarted within a run from the trusted window alone. Anything the carrier heard from it answers a beat. `core.bindFailed` from its running half ends it as failed with `port-taken` or `bind-failed`. A first-use ask it raises as a held `item.on`. It serves `core.status` and `core.views`, hands the core modules each grants snapshot with exec's view of the grants (`execView`) and the notes folder at each `luoshu.pick`, asks the grant risk classifier policy job for a plugin's class and first-use list at an approval, handing it what the plugin reaches through `plugin.call` and where data moves to and from it (`flow`: calls both ways, a subscription from the topic's owner to the plugin that hears it) and clears a plugin's storage through storage while it is on. Every class change goes through one function (`decide`), handed the cause (an approval, a first-party copy, an update, a widen, a narrow, a restore, a remove, a reset, another plugin's change or the pass at start), whether a Confirm for it is on screen and the grant risk classifier policy job's state (`classing`: on, switched off by the human, down any other way). It answers what is stored, the move the Confirm shows and what starts to ask. With the policy job on the policy classes the plugin under the state the change asks for and an item asks unless the entry's `confirmed` record names it, an item being its type with its scope. Switching on an item that asks records it there. An update that applies with no Confirm on screen, a class 0 one on its own or one Confirm-off, empties the record. With the policy job switched off the change passes, the class stays the last one classed, the entry is marked `unclassed` and lists every item not confirmed while the gate is handed no first-use flag while it is off. Down any other way the class is not known and every item asks. A change to one plugin is decided for that plugin and for every other plugin whose links it moves (`changeOf`), so the Confirm names each move up, the changed plugin's own first (`shown`). A restore also shows the screen of the grants it brings back. A move up applied with no Confirm on screen (a first-party copy, a pass, a change applied Confirm-off) that the grant risk classifier says alerts (`alerts`: leaving 0 or entering 4) owes a `class.raised` notice: the entry records it (`owed`: the class last shown, the cause and the plugin changed) in the same write as the class, and the notice is raised from there after the change and at every start (`raiseOwed`) until the human answers it, with Confirm or Cancel, which clears it. A further move keeps one notice from the class last shown. Notices take 16 places of their own, so they never keep the core's other notices out, and one that found no place stays owed and is raised once a notice is answered or at the next start. A plugin never classed, approved while the policy job was off or approved Confirm-off, gets one too: for its notice the class not known counts as 0, everywhere else as 4. The class and its asks are stored already, so the notice approves nothing. The other entries are written in the change's turn, a raised one before the change and a lowered one after (`settle`). At every start, after the first-party reconcile and before the plugin folder is scanned, every plugin-folder entry is decided again from the graph as it stands (`classAll`) and only one that comes out different is written. The same pass runs at once when the human switches the grant risk classifier on again in the run. With the policy job switched off every entry stands as stored in a pass. An entry the role fails for in a pass is stored strict
- `requests.ts`: the security requests: a narrowing change applies at once, a widening or destroying one waits under a core id with the fingerprint of the state it read until the trusted window's Confirm, whose record lands before anything applies
- `graph.ts`: the requires graph as a pure function: cycles refused, a dependent waiting on its first direct requirement that can't serve it and the order every start and stop follows
- `verify.ts`: one read of a plugin folder, its hash and its manifest parsed from the bytes read, with what a read alone can refuse
- `folders.ts`: the plugins manager's folders in the data folder: staging, the swap that puts a copy or an update in place before its entry, the restart marker (`failed-once`) and the marker of each core plugin's version from the last run
- `header.ts`: what it needs from the carrier beyond `register` and `end`, a small interface the tests fake, kept here until the router breaks the loop between the two. `core/backend/wire.ts` builds the two in order. What it needs from the runtime the runtime announces in its own `header.ts`

It imports the state's types from boot's `header.ts`, the runtime's from the runtime's `header.ts` and nothing from the carrier but its `header.ts`. `firstPartyPath` is in `folders.ts`, the one part that resolves install paths
