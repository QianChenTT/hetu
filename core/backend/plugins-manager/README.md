The plugins manager, one of the four parts of the core: what may run, where, when and as whom. It reads the door's code once, reads every plugin folder manifest with the strict parser, reads each plugin's files once and keeps the bytes that run, applies the signer pairing and the reserved ids and places each by where its code came from: the door in a utility process of its own, every plugin sandboxed. It resolves the requires graph, mints every port and registers it with the router in the same step and owns every plugin's lifecycle state. It starts the core modules once the door's code is read, hands them each change and switches them as the human does. It runs no plugin code, decides no grant and restarts nothing on its own. Plain Node, no Electron

`PluginsManager` is one class built as a chain, each file a class holding one job and extending the one below it, each member moved as it was. A step of a part above that a part below calls is declared there as abstract

- `base.ts`: what every part shares: the options, the fields, the constructor, the router's seam (`policyJob` reads a core module's state, the gate and the grant risk classifier among them, an expected guard the human switched off reading off and any other id absent), the small readers and writers every step uses (`note`, `record`, `landing`, `serial`, `bump`, `putEntry`, `writeSwitches`) and how a plugin's status is judged. The door holds no grant. It reads off by the human's switch and refused `missing` when its code couldn't be read. A core module's id names no plugin and a security control is required by no plugin. `holderOf` names the one plugin serving a role's action: its grants hold the role's item, switched on, and it is neither refused nor off, gate on or off. An entry holds its role, on or off, until it is removed, so a plugin asking for a role another holds is refused `role-taken` before any approval, an approval raised while it was found withdrawn, a widen to it is refused and two entries holding one, which only an edited state leaves, are both refused
- `lifecycle.ts`: the requires graph planned again on every change, each plugin's state, the pump that stops in reverse graph order and starts in graph order, starting and stopping incarnations, crashes, the heartbeat's marks and kills, the stops the human asked for and the stopped mode. Every change is told to the router. The door starts before every plugin and its port is registered as the utility process the core started, which the router's floor alone reads for `from: 'door'`. A utility half hears each role a utility half calls in `deps` by the role's action, as its holder is. When that throws it records a fault (`router`, `changed`) and has the router end every open call with power a plugin holds (D-646). Each core module is a node of the graph, ok while on, so a plugin requiring the luoshu waits while it is off or failed. The log failing while hetu runs asks the runtime to quit and start again once
- `identities.ts`: the pairs' state, in memory for the run and in no state file: each pair's items by the root plugin's id and the grant key of the field, so each session of one client shares the client's items, ask and revoke, the pairs the human revoked and a count per pair that an ask waiting for it goes stale against. The ask comes from the plugin the root of a chain called, for that chain's pair. It also raises the ask behind the gate's first-use prompt
- `classes.ts`: every class change goes through one function (`classes`), a change to one plugin or a pass over every entry. It hands the grant risk classifier the whole table (every plugin the plugins manager knows with what it holds and what its entry stores, the change, its cause and whether a Confirm for it is on screen, and for an install of several plugins the others it takes as if installed, with what their staged manifests ask for), checks the answer with the contract's shape check and stores what it answers: the class, the items that ask at first use but those the entry's `confirmed` record names and the notice owed. With the classifier switched off a pass leaves each entry as stored and a change passes: every entry keeps its class, is marked `unclassed` and lists every item not confirmed. Down, a throw or an answer the check refuses, every entry's class is not known and every item asks, since without an answer nothing tells which plugins a change moves. Which entries rise is read from the class numbers stored, never from the classifier: a rising entry is written before the change and a lowering one after it (`settle`). A notice owed is raised from the entry after the change and at every start (`raiseOwed`) until the human answers it. At every start, before the plugin folder is scanned, every entry is classed again (`classAll`) and again once the human switches the classifier on in the run
- `inventory.ts`: the door's code read once from `door.js` beside `main.js` (`readDoor`) and every plugin in the plugin folder found, read once and verified before it runs. An entry that names a signer is refused `signer` until provenance lands, so a folder plugin runs only as the build `allowUnsigned` names, or in dev mode. The door's bytes are not hash-checked: a packaged locked build relies on the ASAR integrity of `app.asar`, a dev or unlocked build loads `door.js` from the built main's folder or from `HETU_INSTALL_DIR` unchecked. Its `plugin.checked` records `unchecked`, never `ok`
- `changes.ts`: applying a change the human confirmed or one that narrows (`applyNow`), grants widened and narrowed, item switches, plugins switched, approved, removed and reset, the numbered grants snapshot with exec's view of it and staged updates resolved against the live graph, each refused unless its version is newer or for an entry naming a signer. An update loads on its own only when the grant risk classifier answers that it does and `allowUnsigned` names its build, so never while the classifier is off or down. An update's Confirm allows its build in the old one's place. A remove takes the plugin's build out of `allowUnsigned` unless another entry names it, and a folder it can't clear keeps its row waiting for approval until a second remove. A `plugin.install`, the Install button's Confirm, is checked against the staging it names when asked for and again as it applies (`stagingOf`): `not-found` for a staging not held, `stale` for a plugin not in it or under another manifest digest, `invalid` for one that can't install and `invalid` with `role-taken` for a role another plugin holds or two plugins ticked would hold and `invalid` with `unapproved` for a plugin whose folder is in the plugin folder with no entry, which an install would replace unseen. Each plugin is classed once by `installClassed`, as the approval or update it is with the others ticked counted as installed. The Confirm's words, the request's fingerprint and the entry stored all come from it, so the class stored is the class shown and a change that moves it between the request and the Confirm stales the request. Its apply (`install`) reads each plugin's bytes again from the staging, refused when they no longer hash to what was staged, classes every one before anything is written, writes each beside the plugin folder, swaps each in with its entry written last, then allows every build in one write. A failure between leaves entries no switch allows, refused `unsigned`. A plugin replaced that runs stops and starts again on its new bytes. The staging is dropped whether it installed or failed
- `plugins-manager.ts`: `PluginsManager` joining the parts: the actions it serves on the router's core seam (`core.status`, `core.views`, `security.list` and the human's stop and restart), what a request's Confirm says (for an install: the source, the unsigned line, then each plugin with its grants as plain sentences and the grant risk classifier's lines under its id, each plugin classed with the others the install takes counted as installed, so the links their manifests declare between them show on the one Confirm), the banner and the start. The start reads the door's code, then runs the core modules. Its checks read the contract's `failSafeControls`: the gate, flood control and every expected guard. A start marker the run before left for one of them means its start hung main, so hetu stops in the stopped mode naming it with the reason `START_HUNG` before any module begins. A marker of a control the human switched off holds nothing back and is cleared. Starting with it switched off clears the marker, Try again clears every marker (`triedAgain`) and Quit keeps it. Shutdown and a clean Quit wait for every marker write and clear under way (`markerWork`). An expected guard no core module holds stops hetu in the stopped mode before any module begins, unless the human switched it off, which `policyJob` reads as off as the router does. Starting with it switched off writes its switch though no plugin holds it. A control that judges yes or no that failed at start stops it before any other module begins or any plugin runs, where the human quits, tries again or starts with it switched off, which counts as switching it off. No restart marker is written for it, so it never starts again on its own
- `requests.ts`: the security requests: the queue, the fingerprint of the state each read, the stale check and record-before-apply. The security view module decides whether a change applies at once, lands its record and applies or waits for the trusted window's Confirm and whether a click counts. With the view off every change a window asks for applies unasked with its record first and the editor window may only switch the view on again. A throw of the view applies nothing and answers `failed`
- the heartbeat, recording and the security view are core modules the plugins manager calls through their doors: it tells the heartbeat each plugin ready, heard and stopped and does the ping, the mark and the kill it asks for, records through recording only while it is on and hands requests to the security view. With the security view off the stopped mode shows in the native box
- `graph.ts`: the requires graph as a pure function: cycles refused, a dependent waiting on its first direct requirement that can't serve it and the order every start and stop follows
- `verify.ts`: one read of a plugin folder, its hash and its manifest parsed from the bytes read, with what a read alone can refuse, and `doorRead`, the door's record built in code: one host entry, asking for nothing, requiring nothing and providing nothing
- `folders.ts`: the plugins manager's folders in the data folder: staging, the swap that puts a copy or an update in place before its entry, the restart marker (`failed-once`) and the start markers (`starting/<id>`, one empty file per judging control whose start runs)
- `connects.ts`: the connect a utility half asks for, held in memory until the same caller collects the human's answer. A connect for a client the core holds already is refused. A client on this computer reaching the door over its local pipe connects with no redirect
- `reads.ts`: the views and plugin rows the router reads
- `header.ts`: what it needs from recording, a small interface the tests fake, and the stagings the Install button's flow made (`Stagings`): what a staging holds, one plugin's bytes read again and checked against the hash staged and the drop. Until main passes stagings every `plugin.install` answers `not-found`. A plugin.install's fingerprint covers the staging, the entry of each plugin it installs and the class each would be stored with, so any of them moving stales it. It calls the router through the router's door and hands it, as it is built, the actions it serves under its part's name, its asks and its listeners for a closed way and for what a half sent, so the router never calls it but through those. `core/backend/wire.ts` builds the two in order. What it needs from the runtime the runtime announces in its own `header.ts`

It imports the state's types from boot's `header.ts`, the runtime's from the runtime's `header.ts`, nothing from the router but `header.ts`, the router's door. It reaches the grant risk classifier through the modules holder's door with its interface typed in the contract (`core/api/classes.ts`)

## Fetching from GitHub

Main's one way to the network, apart from the chain, is `core/backend/lib/github.ts`, shared with the updater. Every window stays offline. Only `stagings.ts` calls the plugins manager's side of it

- `release.ts`: a pasted `https://github.com/<owner>/<repo>` link, its releases page, its latest release or a release by tag read (`githubLink`), the release asked of the API through `core/backend/lib/github.ts`'s `readRelease` (`releaseZips`, 8 MiB and 20 s) and its `.zip` assets uploaded whole answered with their name, size, download link and the sha256 GitHub gives, null when it gives none. A sha256 that is not 64 hex digits refuses the answer. An answer whose download link leaves GitHub's hosts is refused whole. `downloadZip` fetches a picked zip's bytes under 72 MiB, the 64 MiB the unpacking writes at most plus room for a zip's headers, in ten minutes at most, refused before any request when the release says it is bigger and refused as `digest-mismatch` when the bytes downloaded do not hash to the sha256 given. Its answer says whether the bytes were checked (`verified`). The digest comes in the same API answer as the download link, so it is integrity only: it shows the bytes arrived as GitHub holds them and says nothing of who made them

## Staging an install

Apart from the chain, three files put what the human installs into an empty staging folder, read the plugins there and keep each staging until it is installed or dropped

- `unpack.ts`: a zip (`unpackZip`, read once from its bytes with yauzl) or a folder the human picked (`stageFolder`) staged through one writer: every name checked (`nameProblem`: no `..`, absolute or drive name, no backslash, colon, control or Windows-reserved character, no character HFS+ skips, no empty or `.` segment, no trailing dot or space, no Windows device name, at most 1,024 characters, 255 a segment and 32 deep), no name twice once case and Unicode form are folded, links and other special entries refused, encrypted zip entries refused, at most 2,000 entries with every folder a name implies counted and 64 MiB counted as written, every file opened as new. The Finder's `__MACOSX` folder at the top is skipped. A refusal empties the staging folder and says when that failed. The reader turns `\` into `/` before its own name check, so a zip from Windows PowerShell 5.1's Compress-Archive, which writes `\` between segments, unpacks and `..\x` is still refused
- `find.ts`: the plugins in a staging folder, `hetu-plugin.json` at the top or one level down, each read with `readPlugin` against the id its manifest names. A root that is missing, a file or a link is refused, and so are two folders naming one id
- `stagings.ts`: the Install button's stagings in main (`InstallStagings`), each a folder of its own under `<data>/staging/installs`, filled from a zip or a folder main's own dialog picked (`stagePicked`) or from one zip of the latest release found (`findRelease`, `stageRelease`), named by a handle and the zip's place in the list main answered, so the trusted window never sends a path or a download link. Each plugin found is kept with the SHA-256 of its manifest and the hash of its bytes, which `read` checks again before an install. A refusal, a failure or a close on the way clears the folder. At most four stagings are held, the one being made among them, the oldest dropped. One is made at a time, its download included. A run's start sweeps what an earlier run left. The plugins manager's shutdown closes the stagings, stopping every download under way. `plugins-manager.ts` serves `core.findRelease`, `core.stage` and `core.unstage` from it once every plugin may start. Main serves `app.stagePicked` through it, checking first that a pick could be answered and taking one pick at a time. The window is answered each plugin's class as the Confirm would class it with every plugin that can install ticked. A plugin whose folder is in the plugin folder with no entry is answered `unapproved`. A staging the window can't be answered is dropped

Left to the file system, since every file is opened with `wx` and a clash ends in an error, never an overwrite or a write outside the folder: a capital sigma folded as the final sigma where NTFS and APFS take it as the other (`aΣ` and `aσ`), an 8.3 short name standing for a long one (`ALPHAB~1`), and a device name with a space before its dot (`nul .txt`)
