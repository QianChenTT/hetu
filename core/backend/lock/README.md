The lock module, a core module in main that holds note locks: a path, its holder and when it ends. A holder sets a lock for some time. While it holds no other holder's write, remove or move reaches that note. The `leases` community plugin decides who gets one, for which notes and how long

- `lock.ts`: `createLock`, which `wire.ts` makes and the core modules hold. Its provider serves `lock.set`, `lock.clear` and `lock.held`. Its guard answers each write, remove and move in the router's guard step, a move's both ends, from its table alone with no await, `deny` for a note another holder locks, which the router answers `locked`. `role.open` hands it the notes folder as the luoshu gets its own
- `header.ts`: its door, the shapes and the caps the holder and the tests read, and the clocks and publish it is made with

The holder is the chain's own: the root plugin with the whole `onBehalf` field, so each session under one root plugin holds its own locks, or the window for a chain a window began. Never a name in the arguments. Every lock action turns its paths canonical in prepare. The table is keyed by `keyOf` from `core/lib/canonical.ts`, so case, Unicode form and short names of one note meet. `lock.set` locks every path or none, answering `locked` with no holder for a path another holder locks, renews the caller's own locks and cuts a longer time to `MAX_LOCK_MS`. One root plugin's chains hold at most `MAX_LOCKS_PER_ROOT` live locks, and one client under it at most `MAX_LOCKS_PER_CLIENT`, the client being the root plugin with the field up to its first `#` (`grantKeyOf`, as a pair's grants are keyed), so every session of one client counts together and opening more sessions gets no more locks. A window, a content caller and a root plugin calling with no field are each a client of their own, held to the same 256. Four full clients fill the root's 1024, so the root's cap still keeps a plugin's many clients from filling main. Past either cap a set answers `failed` with `quota`. `lock.clear` from a plugin clears only its own chain's locks and answers the same whatever else holds the paths, since it needs no grant. A window clears any, the human taking a note over. `lock.held` names the paths asked about that any holder locks, as the caller spelled them, each with when its lock ends (`until`). Locks live in memory for the run, expired ones go as they are read and another folder frees them all

Each change is told as `lock.changed` with the path, `locked` and `until`, the end in milliseconds since the epoch or null, never the holder: a set that locks a note or moves its end, a clear that frees one, an expiry and another folder freeing them all. It goes out through the router once the step that noticed it ended, so no bus work runs inside a lock action or the guard. Another folder and a release tell at once, the core handing the lock a new folder before the luoshu, so the old folder's notes are judged on the grants that applied to them. It goes only to a plugin the gate lets read the path, as `lock.held` asks, and with the gate switched off by the human to every subscriber, as `luoshu.changed` does. A set's own events reach the bus before its reply, so the plugin that set a lock may hear it first. `until` is read off the wall clock when the event is made, while the lock ends on a monotonic clock that on some systems stops while the computer sleeps, so after such a sleep the lock lasts past the `until` told. `lock.held` reads each end again when asked. Nothing runs on a timer, so an expiry is told only once a check, a lock action on the note, a set by the same root plugin or another folder meets it, which can be never. Switched off or failed, the module guards nothing, so the core has it release every lock, each told unlocked at once, and it starts empty when on again. A plugin that must act at the end sets its own timer on `until`. Events are deltas: a plugin told `events.dropped` for `lock.changed`, past its credits or after the gate was down, asks `lock.held` again for the notes it follows and rebuilds its locks and timers from the ends it answers

A known limit: a write that passed the guard before a `lock.set` on its note can still land after the set returned, since the guard answers before the luoshu's perform and the set takes no latch

Roles: `lock.ts` policy holder, since it says yes or no and the router enforces, `header.ts` contract
