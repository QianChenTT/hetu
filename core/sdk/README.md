`@hetu/sdk`, what a plugin imports. A plugin writes `definePlugin({ start, stop })` and gets one call per action, a typed `Refused` and its own actions and events, with the transport and the messages hidden. It holds no security: every check stays in the carrier and a plugin that posts raw messages gets the same refusals. What a plugin bundles from it reaches neither zod nor Node, which a test checks by bundling `index.ts`

- `plugin.ts`: `definePlugin` and `run`, which the runtime calls on a half's transport. `init`, `ready`, `deps`, the heartbeat and `stop` within its grace
- `calls.ts`: the half's own calls. Past `callsInFlight` a call waits its turn, `starting` and `throttled` are tried again within the deadline, a call with no reply settles `timeout` a second past its deadline and an aborted signal sends `cancel`
- `client.ts`: the typed client, one method per provider action in `core/api` (`ctx.luoshu.read`, `ctx.storage.set` and the rest) and `call` for another plugin's `<target>.<name>`
- `serving.ts`: the plugin's own actions, `provide`, `filterReadable` and the incoming call with its signal and a client whose calls name it as their parent
- `events.ts`: subscriptions, one per topic whatever the number of handlers, acks after each 64 handled and once idle, `onResync` for `events.dropped` and one subscribe again for `events.ended`
- `transport.ts`: the transport a half runs on, in the loader's `HostLink` shape. The pacing keeps every message under 90% of `messagesPerSecond`
- `worker.ts`: `runInWorker`, which waits for the worker host page's `{ v: 1, kind: 'port' }` message and runs the plugin on that port, then hands each `{ v: 1, kind: 'drawer' }` port to `ctx.editor`. Its transport sends and reads JSON text, since the relay in the page passes nothing else. It weighs each message as the relay does and throws for one the relay would refuse, so a reply fails rather than get the plugin cut off. It is the worker's only pacer: one queue held to 90% of both the message rate and the byte budget, a pong going first, and lowered limits from the page applying from then on
- `editor.ts`: `ctx.editor`, a worker's side of the editor bridge: `instances`, `read`, `decorate`, `edit`, `bind`, `keys` and events by topic, on the worker's port to the editor page's drawer. Every call answers `unavailable` while there is none. On each new port it sends its bindings and key stream again and fails what was in flight on the old one
- `ui.ts`: `ctx.ui`, on the same port: `views.open`, `close`, `title`, `draw`, `post` and `bind`, `layout.draw` and events by topic. A plugin draws a whole tree each time and the SDK sends what changed, the whole tree past 100 operations or after a refusal. A new port forgets every tree, since a new page numbers instances afresh. Events that come before the plugin's start ran wait for it, at most 1,000, so the first `view.opened` and `layout.state` reach the handlers start registers. `ctx.editor.open` opens a note inside the plugin's read or list scope
- `frame.ts`: `@hetu/sdk/frame`, a frame's script's side: `frameChannel()` takes the port the drawer sends on its first load and talks JSON text to its own plugin's worker. Frame scripts are classic, since module scripts don't run in a view
- `plain.ts`: the plain data check a call's arguments and results pass before they leave, with the same depth and key rules as `core/api`
- `refused.ts`: `Refused` and `attempt`, which `ctx.try` is
- `testing/`: `@hetu/sdk/testing`, a fake core for a plugin's tests: the real carrier with a gate per mode (the manifest's grants, allow all, deny all, gate failed, a requirement missing), the luoshu, storage and cache in memory, answering after `latencyMs` when a test sets it, the human's `limits` a test may change while the plugin runs and test callers with the grants a test names. `FakeDrawer` is an editor page's drawer in memory: the plugin's views and skeleton applied, notes a test opens served through the editor bridge and events a test sends
- `build/esbuild.ts`: `@hetu/sdk/esbuild`, one classic script per worker and view, each output named in `workers` wrapped in `runInWorker` so a plugin only exports `definePlugin(...)`, refusing a Node built-in anywhere in the import graph and a bundle holding `eval`, `Function` or a timer given a string. `checkHostImports` holds a host half to its manifest's `node` list
- `build/check-manifest.ts`: `@hetu/sdk/check-manifest`, the problems the loader would refuse a manifest for, also a command: `node core/sdk/build/check-manifest.ts <dir> [--install] [--built]`
