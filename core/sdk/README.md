`@hetu/sdk`, what a plugin imports. A plugin writes `definePlugin({ start, stop })` and gets one call per action, a typed `Refused` and its own actions and events, with the transport and the messages hidden. It holds no security: every check stays in the router and a plugin that posts raw messages gets the same refusals. What a plugin bundles from it reaches neither zod nor Node, which a test checks by bundling `index.ts`. `index.ts` also hands on `isDotName` from `core/api/names.ts`, for a plugin that keeps paths from an older build, and `actionPathProblem` from `core/api/paths.ts`, the path check the action schemas refuse by

- `plugin.ts`: `definePlugin` and `run`, which the runtime calls on a half's transport. `init`, `ready`, `deps` with `onDeps` hooks run on each change to the map after `has` reads the new one, the heartbeat and `stop` within its grace. The context holds what any half may use and no data folder. `mcp-http-handler`'s utility half tells a failed bind as a raw core call, `ctx.call('core', 'bindFailed', { reason })`, which the floor refuses to every other caller
- `calls.ts`: the half's own calls. Past `callsInFlight` a call waits its turn, `starting` and `throttled` are tried again within the deadline, a call with no reply settles `timeout` a second past its deadline and an aborted signal sends `cancel`
- `client.ts`: the typed client, one method per provider action in `core/api` (`ctx.luoshu.read`, `ctx.storage.set` and the rest) and `call` for another plugin's `<target>.<name>`
- `serving.ts`: the plugin's own actions and a role's it holds (`provide`, a role under its own action such as `door.handle`, from `roleActionNames`), `filterReadable` and the incoming call with its signal and a client whose calls name it as their parent
- `events.ts`: subscriptions, one per topic whatever the number of handlers, acks after each 64 handled and once idle, `onResync` for `events.dropped` and one subscribe again for `events.ended`. A `lock.changed` handler hears `LockChangedEvent`, the path with `locked` and `until`, every other topic a `PathEvent`
- `transport.ts`: the transport a half runs on, in the plugins manager's `HostLink` shape. The pacing keeps a half's messages under 90% of `messagesPerSecond` counted over 1.1 s, so main reading one late in its own 1 s window never drops it
- `worker.ts`: `runInWorker`, which waits for the worker host page's `{ v: 1, kind: 'port' }` message and runs the plugin on that port, then hands each `{ v: 1, kind: 'drawer' }` port to `ctx.editor`. Its transport sends and reads JSON text, since the relay in the page passes nothing else. It weighs each message as the relay does and throws for one the relay would refuse, so a reply fails rather than get the plugin cut off. It is the worker's only pacer: one queue held to 90% of both the message rate, counted over 1.1 s as the transport's, and the byte budget, with a pong going first. Limits the page sends again once the human sets one apply from then on
- `editor.ts`: `ctx.editor`, a worker's side of the editor bridge: `instances`, `read`, `decorate`, `edit`, `bind`, `keystream`, `viewports` and events by topic, `link` among them, which a plugin hears when the human Ctrl+clicks, Cmd+clicks on macOS, a link mark it placed with `{ kind: 'link', from, to, id }`, on the worker's port to the editor page's drawer. Every call answers `unavailable` while there is none. On each new port it sends its bindings, key stream and ask for ranges again and fails what was in flight on the old one
- `ui.ts`: `ctx.ui`, on the same port: `views.open`, `close`, `title`, `draw`, `post` and `bind`, `layout.draw` and events by topic. A tree may hold `{ kind: 'image', id, path, alt? }`, a png, jpeg, gif, webp, avif, bmp or svg note the drawer shows only inside the plugin's `luoshu.read` scope, never handing the plugin its bytes. A plugin draws a whole tree each time and the SDK sends what changed, the whole tree past 100 operations or after a refusal. A new port forgets every tree, since a new page numbers instances afresh. Events that come before the plugin's start ran wait for it, at most 1,000, so the first `view.opened` and `layout.state` reach the handlers start registers. `ctx.editor.open` opens a note inside the plugin's `luoshu.read` scope
- `frame.ts`: `@hetu/sdk/frame`, a frame's script's side: `frameChannel()` takes the port the drawer sends on its first load and talks JSON text to its own plugin's worker. Frame scripts are classic, since module scripts don't run in a view
- `plain.ts`: the plain data check a call's arguments and results pass before they leave, with the same depth and key rules as `core/api`
- `refused.ts`: `Refused` and `attempt`, which `ctx.try` is
- `testing/`: `@hetu/sdk/testing`, a fake core for a plugin's tests, which refuses a manifest whose `api` range the core leaves out as the plugins manager does: the real router with a gate per mode (the manifest's grants, allow all, deny all, gate failed, a requirement missing), the luoshu (read, write, remove, move and list, a listing paged and filtered by the router's `canList` as the luoshu plugin's is, its folder matched in the case it is written), storage and cache in memory, history in memory over the luoshu's notes (`commit`, `log` and `read`, answering as the history module does, a commit named by `core/api`'s `signatureOf` as the module's are and the commit and read grants judged apart by path), each answering after `latencyMs` when a test sets it, the lock module's own table and guard (`lock.set`, `lock.clear` and `lock.held` answering as the module does, `lock.held` with `{ locks: [{ path, until }] }`, its holder, caps and expiry on the `clock` a test names, `lock.changed` told as the module tells it with each end on that clock, to a plugin that reads the note, and a write, remove or move onto a note another holder locks refused `locked`, as the router answers the guard, the lock's paths taken as spelled where hetu makes them canonical), the human's `limits` a test may change while the plugin runs, test callers with the grants a test names, a caller's `onBehalf` with its pair's `pairGrants`, which a call under it needs too as the gate judges a pair, and stand-ins for other plugins (`standIn`, `setState`), whose declared `from` lists the real router enforces, one of them holding a role (`roles`), which a utility half under test calls and hears in `deps` by the role's action. `door` plays hetu's door for a plugin under test granted `door.handle`: the role given to it and a port placed `utility`, its `handle` one `door.handle` call on behalf of a label, with that label's client holding `pairGrants` when named. `mcp-http-handler` under test runs on a port placed `utility`, as the plugins manager places it and `coreCalls` and `status` show a `core.bindFailed` it made. `FakeDrawer` is an editor page's drawer in memory: the plugin's views and skeleton applied with `core/api`'s own checks, an image node's path among them, notes a test opens, which count as the human's, served through the editor bridge and events a test sends. Where the human is goes as hetu's drawer sends it: `viewport` moves a note's drawn range, which reaches the plugin only after its `viewports(true)` and only for a note it reads, the range drawn then coming at the ask and at `openNote`. `command` fires a command only when the plugin bound a key to it, with the selection only for a note it reads. An edit is told back as the note's next change and places the cursor, read with `selection`, only in answer to the last command on that note at its version and inside the range it changed. `type` makes a change as the human, which a plugin reading the note hears as `editor.changed` unless the test says it was lost, and moves the plugin's link marks as hetu's drawer does. `closeNote` closes a note, told only to a plugin that marked it as hetu's drawer tells it. `clickLink` Ctrl+clicks a note at a place or on the plugin's link of an id, the smallest link there told and none on a tie, only while the plugin reads the note and holds `ui.decoration`. A click on no link changes nothing. `delay` holds a verb's answers until let go and `refuseNext` refuses its next call with a code. `calls` lists the verbs the plugin called and `versions` the version each set of marks came for
  Where the fake differs from real hetu, so a plugin that passes here can still fail there:
  - marks other than links stay as sent when the test types, where hetu's drawer moves them with the text
  - paths are never made canonical: no refusal for a dot name or a path outside the notes folder and no case folding
  - history never answers `not-text`, `timeout` or `unavailable`
  - history's commit ids are SHA-1 hashes of its own, its dates are in UTC and `too-large` counts a note in UTF-8 bytes
- `build/esbuild.ts`: `@hetu/sdk/esbuild`, one classic script per worker and view, each output named in `workers` wrapped in `runInWorker` so a plugin only exports `definePlugin(...)`, refusing a Node built-in anywhere in the import graph and a bundle holding `eval`, `Function` or a timer given a string. `checkHostImports` holds a host half to its manifest's `node` list
- `build/check-manifest.ts`: `@hetu/sdk/check-manifest`, the problems the plugins manager would refuse a manifest for, also a command: `node core/sdk/build/check-manifest.ts <dir> [--install] [--built]`
