The door agents come in through: a core plugin whose host half runs in a utility process and listens on `127.0.0.1:4747` with Node's own HTTP/1.1 server. Every request meets the checks in a fixed order before anything else reads it

- **Host.** Exactly one Host header reading `127.0.0.1:4747`, compared as sent, and a target that is a path. No Host, another name or port, `localhost`, a trailing dot, userinfo, another spelling of the address, two Host headers and an absolute target all answer 403. This is the DNS rebinding check
- **Origin.** Any Origin header answers 403, `null` and the door's own origin included. `Sec-Fetch-Site`, when sent, must be one header reading `none` or `same-origin`
- **Route.** `POST /mcp` over HTTP/1.1 with the exact path and no query. `GET` and `DELETE` on `/mcp` answer 405 naming `POST`, every other method or target 404, another version 505 and a request asking to upgrade 400
- **Rate.** 50 requests a second, counted only for requests that passed the checks above, then 429
- **Size.** 8 KiB of headers (431) and 512 KiB of body (413), the declared length read before the body and the body counted as it arrives
- **Token.** A seam from the `Authorization` header's text to a client. Two `Authorization` headers count as none. The build that ships issues no token, so it answers 401 with a bare `WWW-Authenticate: Bearer`
- **Node's limits.** The strict parser, 5 s for headers, 35 s for a request, 5 s keep-alive, 100 requests a socket and 64 connections. A missing Host is left to the door's own check. A `CONNECT` meets the checks and is refused with the door's own answer, never tunnelled, an `Expect` other than `100-continue` answers 417 once the checks before the rate passed, both recorded and closed, and an upgrade is never taken. A request Node read behind a refused one on the same socket is never checked or served and a socket that closes cancels every call it carried. A socket the door answers itself past Node's response, a `CONNECT` or a parser failure, gets that answer only after every answer it owes to a request read to its end, so it is never read as the answer to an earlier request. The socket is destroyed once the answer is flushed and at the latest 35 s after the refusal, whatever the client does, a call still owed then cancelled with it

Only a request past every check but the label's is read to its end. A token naming a label outside `<client id>#<n>` is then answered 401 as `token`, and any other is handed on with the client the token named. Every response carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and a CSP of `default-src 'none'` and `frame-ancestors 'none'`, the 400, 408 and 431 the door writes for Node's parser included. Node's own 503 to a request past 100 on one socket carries none of them and no body, and a connection past 64 is dropped unanswered. No `Access-Control-*` header and nothing a request sent ever reaches a response header, and an answer handed back sets only its status and body. A refusal is told by one of eight fixed reasons, `host`, `origin`, `method`, `size`, `rate`, `token`, `malformed` for bytes the parser or the door's own reading refused and `timeout` for a request too slow, each socket's parser failure once, and the core hears them counted by reason at most once a second through `core.refused`. The door writes no line anywhere and never records a Host, an Origin, a target, a token or a body. The bind takes 127.0.0.1 and the port named or fails, with no other port tried

Behind the door a request becomes one `mcp.handle` call on behalf of the label the token named: the client id, `#` and the number of the authorization with no leading zero, the client id within 255 of the characters a URL holds as written and the number within 15 digits. A label out of that form answers 401 and is recorded as `token`, since the core takes any field and the form is the door's own check. The body goes as text and is never parsed, a body that isn't UTF-8 answering 400. Only the `mcp-` headers go with it, at most 32, a name within 64 bytes and a value within 256 (431), one name sent twice answering 400. Past 8 calls in flight for a client or 32 in all the door answers 429. Each of these is recorded and closes the connection. MCP answers a status of 200, 202, 400 or 404 and a body of text or null within 4 MiB and sets no header, anything else answering 502. A call MCP or the core refused answers 503, 504, 429, 413 or 502 with a fixed body that never names the code, keeps the connection and is no refusal at the door

The door is open exactly while `mcp` is there: bound on start and on every change the core tells, closed when `mcp` goes. A bind that fails tells the core `port-taken` or `bind-failed` through `core.bindFailed`, which ends the half, and no other port is tried

`src/checks.ts` holds the checks as plain functions over the raw request and the limits as named constants. `src/server.ts` is the server, `src/mcp.ts` the serving part behind it, `src/report.ts` the refusals counted for the core, `src/keeper.ts` the plugin that opens and closes the door and `src/host.ts` the host entry on 127.0.0.1:4747 with a token seam that refuses every token
