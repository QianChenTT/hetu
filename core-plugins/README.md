One package per plugin with one manifest and one identity. Its entries say where each half runs: `worker` in a hidden renderer and `frames` in a window. A core plugin, loaded only from the install, may also have `page` in a window and `host`, which runs in a utility process of its own and never in main. The manifest names `requires` and `provides`, core plugins also `guards` and `node`

The core plugins built so far are mcp-http-handler and hidden-marks. `mcp-http-handler/` is the HTTP door MCP clients are to come in through, a host half in its utility process. It checks the form of the label each token names and hands every request on as one `mcp.handle` call with that label as `onBehalf`. It is bound only while an `mcp` plugin is there and none is built yet. `hidden-marks/` holds the manifest of the in-page plugin whose module the editor page compiles in from the install. Leases and net are designed and not built

The gate, the grant risk classifier, flood control, the heartbeat, recording, the security view, storage, the luoshu, history and exec are no plugins. They are core modules in `core/backend`, bundled into `main.js`, each with its own switch. No plugin runs in main. CodeMirror is the editor window's own, no plugin

`search/` is first-party search and `layout/` hetu's own layout, both built on `@hetu/sdk` and tested on its fake core, the layout on its fake drawer too. Both run sandboxed as first-party copies in the plugin folder. The file explorer isn't here: it lives in `file-explorer/` of the community repository `QianChenTT/hetu-plugins`, which hetu's build takes as a dev dependency at one pinned commit and builds as a first-party plugin with hetu's own SDK (`core/build/README.md` says how the commit is pinned and moved). A plugin may declare `views` drawn as trees or frames and a `theme` of token values in its manifest. Git, artifacts and MCP are designed to run sandboxed and aren't built
