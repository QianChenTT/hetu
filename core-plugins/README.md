One package per plugin with one manifest and one identity. Its entries say where each half runs: `worker` in a hidden renderer and `frames` in a window. A core plugin, loaded only from the install, may also have `host`, which runs in a utility process of its own and never in main. The manifest names `requires`, `provides`, `views` and a `theme`, core plugins also `guards` and `node`

One plugin lives here. `mcp-http-handler/` is the core plugin MCP clients are to come in through, a host half in its utility process with two doors: HTTP on `127.0.0.1:4747` and a local pipe that the shim `hetu.exe --mcp-stdio` relays an agent's stdin and stdout over. Each request meets the door's checks and goes on as one `mcp.handle` call with the client's label as `onBehalf`. The HTTP door answers every token 401, since the build that ships issues none. A client on the pipe joins once the human confirms it. Both doors are open only while an `mcp` plugin is there and none is in this repo. Leases and net are designed and not built

The gate, the grant risk classifier, flood control, the heartbeat, recording, the security view, storage, the luoshu, history, exec and the lock are no plugins. They are core modules in `core/backend`, bundled into `main.js`, each with its own switch. No plugin runs in main. CodeMirror is the editor window's own, no plugin

hetu ships no other plugin. The layout, hidden marks, search and the file explorer are community plugins the human installs and approves, each a worker in a hidden renderer of its own. With no layout picked the drawer draws its plain layout, and the first layout that comes while none is picked is picked. A data folder from an older build that holds one as a first-party copy keeps it in the plugin folder refused with `signer` and runs no worker for it until the human resets it and approves it again. A plugin may declare `views` drawn as trees or frames and a `theme` of token values in its manifest. Git, artifacts and MCP are designed to run sandboxed and aren't built
